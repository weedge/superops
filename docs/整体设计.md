# Popto 产品运营研发多 Agent 系统 · 整体设计

这篇是一页纸的全景：设计原则、分层与模块、主要的交互流程。概念的定义在 [001 领域模型](001-domain.md)，授权在 [002 授权](002-authorization.md)，一轮怎么跑在 [003 执行](003-execution.md)，代码索引在 [007 架构](007-architecture.md)，会话在 [009 会话](009-sessions.md)，四条业务流水线的细节在 [整体流程](整体流程.md)。面板“设计”页展示的就是这篇。

## 一、整体设计

**一句话**：事件进来，系统判断该不该开工；开工的事在一张“工单”里由本机的 Agent（Claude / Codex / Antigravity）或确定性脚本做完；只有要人拍板的事，才变成一张带选项的卡片发到钉钉群。

**贯穿全局的原则**

1. **少占人的注意力**：进展不汇报，结果按规则的 `tell` 决定发不发，要人决定的事只通过卡片找人。
2. **对外动作必须人批**：发布、发评论、合并、删除这类事件，Agent 自己发不出去，只能写成卡片选项；人选中后，宿主带着“谁、哪张卡、哪个选项”的批准凭据去执行。
3. **没人要求的事要有成文规则**：`policy.yaml` 里的规则（目前 51 条）决定什么事件开什么工单；接单模式 `off` / `observe` / `auto`。
4. **外部内容一律是数据**：评论、网页、帖子都包在不可信数据区里，处理它们的规则用只读档位。
5. **引擎是唯一的写入方**：触发、线程、决定、工单、派工只由领域引擎写；外部动作先记进库，事务提交后再执行，失败按退避重试。

## 二、分层与模块

```text
┌─ 人 ─────────────────────────────────────────────────────────────────────────┐
│ 钉钉运营群（回 T12 1 批卡片）   面板 :8797   命令行 superops ...             │
└──────────────────────────────────────────────────────────────────────────────┘
        │ 群消息 / 卡片回调 / 管理 API /api/*
        ▼
┌─ 1 来源层 sources/ ──────────────────────────────────────────────────────────┐
│ schedule 定时   pipeline 业务事件   cli 终端   dingtalk 钉钉   lark 飞书     │
│ 钉钉 / 飞书单聊、@我 -> 自动回复（只读起草，以你的身份回，不开工单）         │
└──────────────────────────────────────────────────────────────────────────────┘
        │ 触发 trigger（属于一个或多个线程）
        ▼
┌─ 2 领域引擎 core/  唯一写入方，同步、事务 ───────────────────────────────────┐
│ Intake 收触发、扇出给订阅的工单 -> Evals 成批评估                            │
│ -> Tickets 工单生命周期 -> Assignments 派工与报告 -> Replies 消息与问题      │
└──────────────────────────────────────────────────────────────────────────────┘
        │ 研判 / 执行 / 发消息 / 记状态
        ▼
┌─ 3 应用层 app/ ──────────────────────────────────────────────────────────────┐
│ Runtime 组合根（每 2 秒一轮 pass）   Settings 策略与接单模式                 │
│ Assessor 研判：规则直配 / 主 Session   Store + Effects 状态与副作用队列      │
│ Outbox 发消息（静默、卡片上限）   http 管理 API   views 面板数据             │
└──────────────────────────────────────────────────────────────────────────────┘
┌─ 4 执行层 executor/ ─────────────────────────────────────────────────────────┐
│ TicketExecutor 跑一轮：准备目录、上下文、worktree、浏览器 -> 校验 -> 入库    │
│ AgentPool 降级链、并发、熔断、忙时顺延   breaker 错误归类                    │
│ adapters：Claude / Codex / Antigravity / 脚本（权限档位、续接、超时）        │
└──────────────────────────────────────────────────────────────────────────────┘
        │ 一轮：Agent 命令行 或 确定性脚本
        ▼
┌─ 5 业务层 biz/ ──────────────────────────────────────────────────────────────┐
│ collectors 采集   executors 发布 / 回复 / 线索评论 / 清理   ci 审查合并      │
│ ingest 产出入库   context 上下文   agent_browser   retention 数据保留        │
│ -> ops.db：内容、作品、指标、评论、需求、线索、竞品                          │
└──────────────────────────────────────────────────────────────────────────────┘
┌─ 基础设施 infra/  各层共用，不依赖业务 ──────────────────────────────────────┐
│ instance 部署名   paths   config   timeutil   validate   redact 打码         │
│ governance 决策档案   secrets 钥匙串   notifier 钉钉 / 飞书发送渠道          │
└──────────────────────────────────────────────────────────────────────────────┘

配置与内容：policy.yaml   schedules.yaml   agents.yaml（含 instance）/ local.yaml
           prompts/   skills/ops-*（SKILL.md + schema.json）
           decisions.md   not-doing.md   listening/keywords.yaml
```

| 层 | 主要模块 | 职责 |
| --- | --- | --- |
| 1 来源 | `sources/schedule.py`、`pipeline.py`、`cli.py`、`dingtalk.py`、`lark.py` | 把定时、业务事件、终端里的话、钉钉 / 飞书群消息和卡片回调统一成“触发”；每条触发属于一个或多个线程。飞书以本人身份轮询 |
| 2 引擎 | `core/intake.py`、`evals.py`、`tickets.py`、`assignments.py`、`replies.py` | 存触发、扇出给订阅的工单；成批评估；建工单（授权、订阅、派工）；记报告、问题和人的回答；结束、恢复、停止 |
| 3 应用 | `app/runtime.py`（组合根，每 2 秒一轮 pass）、`assessor.py`、`settings.py`、`store.py`、`effects.py`、`outbox.py`、`http.py`、`views.py`、`prompts.py`、`preflight.py`、`autoreply.py` | 研判（规则直配或主 Session）、策略与模式、副作用队列、发消息、管理 API、面板数据、拼提示词、启动检查、钉钉自动回复 |
| 4 执行 | `executor/worker.py`、`pool.py`、`adapters.py`、`breaker.py` | 跑一轮：准备工单目录、上下文、worktree、浏览器 → 选 Agent（降级链、并发、熔断、忙时顺延）→ 按权限档位调命令行（续接会话、超时、无动作提前结束）→ 校验 → 入库 → 发事件 → 报告 |
| 5 业务 | `biz/collectors/`（metrics、comments、listening、competitors、funnel、creator、tikhub）、`biz/executors/`（publish、publishers、reply、leads、comment、cleanup）、`biz/ci/`、`ingest.py`、`context.py`、`db.py` | Popto 的确定性业务动作和数据：采集、发布、发评论、合并、入库、上下文提供 |
| 基础设施 | `infra/instance.py`、`paths.py`、`config.py`、`timeutil.py`、`validate.py`、`redact.py`、`governance.py`、`secrets.py`、`notifier/` | 各层共用、和具体业务无关：部署名推出数据目录 / 钥匙串服务名 / launchd 标签 / 积分计数器，读配置、校验输出、打码、决策档案、发钉钉 / 飞书消息 |
| 面板 / 命令行 | `panel/index.html`、`cli.py` | 给人看和操作，全部走管理 API |

**数据放在哪**

| 位置 | 内容 |
| --- | --- |
| `superops.sqlite` | 宿主状态：触发、线程、决定、工单、副作用、发件箱、会话 ID |
| `ops.db` | 业务数据：内容、作品、指标、评论、需求、线索、监听结果、竞品数据、上线核实 |
| `work/<工单短名>/` | 每张工单的目录：每轮的提示词、上下文、Agent 产出 |
| `runs/` | 脚本工单的任务文件和输出 |
| `browser-profiles/` | 各平台的登录态和专用浏览器 |

## 三、交互流程

### 1. 一条事件的一生

```text
来源 ──触发──► Intake ──► 线程上有订阅的工单？──是──► 作为输入送给它（不再评估）
                              │否
                              ▼
                        Evals 排队、成批评估
                              │
                     Assessor 研判（四选一）
                ┌─────────────┴──────────────┐
          命中规则的事件：直配             人的请求 / 语义规则：主 Session
                └─────────────┬──────────────┘   （每个候选一次独立模型调用）
               接单 / 转给已有工单 / 停止 / 忽略
                              │接单
                              ▼
          Tickets：建工单（授权、订阅线程、第一次派工）
                              │ Effects：提交后启动
                              ▼
TicketExecutor：准备目录和上下文 → AgentPool 选 Agent → adapter 跑一轮
                              │
                  报告 {state, summary, question, events, output…}
                              │
      ┌─────────────┬─────────┴────────┬───────────────┐
  校验并入库      events → pipeline   question → 卡片   state
  ingest→ops.db  （成为新触发，        Outbox 发到群   ready 结束 / waiting 等
                  推动下一环）                          blocked·failed 告诉人
```

### 2. 人批红：对外动作的唯一入口

```text
卡片发到群 ──► 人回「T12 1」或「T12 1 2,5」（只批几条）
   ──► dingtalk 来源 ──► Runtime.answer_by_code ──► Engine.answer
   ──► attention.answered ──► Runtime 发出选项里的事件
         （每条带批准凭据：谁、哪张卡、哪个选项；按明细序号去重）
   ──► pipeline ──► requires_approval 的规则才接
   ──► 脚本执行器：发布 / 发评论 / 合并 / 清理 ──► 结果按 tell 发回群
卡片到期 ──► 按 on_expire 的安全选项处理（不带凭据，不会触发对外动作）
```

### 3. 一张工单里的多轮

```text
第 1 轮：完整提示词（角色、团队、Skill、相关决定、上下文、起点）
   ↓ 报告 waiting / question
人回答、或线程上来了新事件 ──► 作为输入送达
   ↓
第 2 轮起：同一 Agent 续接会话（Claude --resume / Codex exec resume）
          提示词换成精简版 + “这张工单到目前为止”
   ↓
报 ready：没有跟随线程、也没有新输入就结束；有新输入就再跑一轮
换 Agent（降级）或续不上：新开会话，用完整提示词加摘要兜底
```

### 4. 四条业务流水线

```text
内容     周五选题 → 卡片人批 → 写稿 → 合规复核（Codex，最多 2 轮）→ 发布包
         → 17:00 待发布卡片 → 人批 → 发布（live / draft / dry_run）→ 登记作品

数据回收 发布 → 排 1h / 24h / 72h / 7d 采集 → 每 30 分钟采到点的 → 异常 → 单条复盘
         手动：面板“立即采集” / superops metrics collect

需求开发 需求信号（评论、自用摩擦、人说“需求：”、竞品评论评审）→ 需求池
         → 周一 Top 10 卡片 → 人批 → 写 PRD → 人批 → worktree 开发、commit
         → 宿主推送开 MR → Codex 审查（最多 3 轮，打回回到同一张工单改）
         → 合并闸门 → 卡片 → 人批合并 → 核实上线（没配地址就请人确认）

获客     14:00 接口监听（抖音 / 小红书 / 视频号 / 快手；人群词找人）
         14:10 浏览器补位（知乎 / B站 / 搜狗微信）
         → Claude 判断线索、写评论原文 → 补粉丝数、粉丝不足的不上卡
         → 今日线索卡片 → 人批“跟进并发评论” → 品牌号在抖音发评论
         周四：竞品评论 → 候选需求评审卡片（带来源作品）→ 进需求池
         每 28 天：竞品调研报告（官网、定价、社媒，每条附来源）
```

### 5. Agent 工单和脚本工单

| | Agent 工单 | 脚本工单 |
| --- | --- | --- |
| 用在 | 写作、分拣、研判、审查、开发、浏览器操作 | 采集、登记、发布、回复、合并、清理、出卡片 |
| 输入 | 提示词：规则、Skill、上下文、本轮输入 | `runs/<短名>/task.json` |
| 输出 | JSON 报告，按 Skill 的 schema 校验 | stdout 最后一行 JSON：`status`、`decision_card`、`follow_up_events` |
| 发事件 | 不可信：需要人批的类型会被拦下 | 可信：带宿主令牌 |
| 重跑 | 被人的消息唤醒后接着做 | 绝不因为一句话重跑；要重跑用“重试”或重新触发 |

### 6. 可靠性兜底

- 副作用先落库、事务提交后执行，失败按指数退避重试。
- 宿主重启：先关端口再等工单收尾；新进程绑不上端口会等旧进程释放；还在跑的那一轮带恢复说明重来。
- Agent 超时、浏览器类工作 10 分钟没有任何动作、额度用尽、登录失效：熔断或换降级链上的下一个 Agent。
- 晚到的事件交给进行中的工单；工单报 `ready` 时还有没处理的输入，就再跑一轮。
- 卡片批准发出的事件按明细序号去重，同类型同主题的几条不会被当成重复。
- 合并后核实线上版本；品牌号发评论跨工单排队、每天有上限、不重复发。
