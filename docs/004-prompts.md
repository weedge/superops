# 004 提示词

这篇讲 Agent 读到什么、团队能改什么、改了什么时候生效。它建立在 [000 理念](000-philosophy.md) 到 [003 执行](003-execution.md) 之上。

Agent 没有常驻的会话，也没有可调用的宿主工具：每一轮是一次独立的命令行调用，宿主把这一轮该知道的一切拼成一份提示词从标准输入给它，它的全部输出是一个 JSON 对象。所以“Agent 读到什么”就是这份提示词，加上它在工作目录里能打开的文件。每一轮实际发出的提示词原样存在工单目录的 `turn-NNN-<agent>.md`，要知道 Agent 当时看到了什么，打开它。

## 团队写什么

| 写在哪 | 管什么 | 改了之后 |
| --- | --- | --- |
| `prompts/team/communication.md`「沟通」 | 什么时候找人、消息怎么写、卡片怎么写 | 下一轮生效 |
| `prompts/team/scope.md`「工单范围」 | 工单做到哪、什么情况下带着草稿停下 | 下一轮生效 |
| `prompts/team/delivery.md`「交付要求」 | 产出放哪、结论要什么证据、开发任务和 MR 的规矩 | 下一轮生效 |
| 规则的 `instruction`（`policy.yaml`） | 这一类主动工作允许做什么。它是工单的范围，也原样给执行器 | `superops reload`；策略版本会变，依据它的未结束工单会被告知 |
| Skill：`skills/<名字>/SKILL.md` + `schema.json` | 一类工作的步骤、产出格式和结构化字段 | 下一轮生效 |
| `decisions.md` / `not-doing.md` | 人亲口定的事、定了不做的事和回复口径 | 下一轮生效；群里说「记下来：……」会追加 |
| 规则的 `run.context` | 这类工作开工前往 `context/` 里放哪些参考材料 | `superops reload` |
| `prompts/auto-reply.md` | 钉钉自动回复的规矩：怎么说话、哪些事不替我做主、不可信输入 | 下一条消息生效 |
| `~/popto-superops-data/auto-reply-context.md` | 我的近况（这周在做什么、到哪一步、下一步），自动回复只按这里和进行中的工单标题回答工作进展。在数据目录里，不进 git | 下一条消息生效 |

内置文字在 `prompts/*.md`：两个角色（`shared.md`、`orchestrator.md`、`worker.md`）、订阅与回复（`subscriptions.md`、`replies.md`）、路由与研判（`dispatch.md`、`admission.md`）、怎么工作（`work.md`）、需要人决定时（`handoff-worker.md`）。它们也是仓库里的文件，每次拼提示词时现读，改了下一轮就生效；但它们讲的是宿主的机制，改之前先确认代码确实那样做。内置文字用标题引用团队三段，不重复它们的内容。

提示词文件一行写一句，连续的行拼成一段，空行分段；列表、标题、表格和代码行保持原样。

输出格式的说明（报告和路由决定各有哪些字段）在代码里：`superops/app/prompts.py` 的 `REPORT_GUIDE` 和 `ROUTE_GUIDE`，和校验用的 Schema 放在一起，改一处必须同时改另一处。发给人的卡片怎么渲染、输入怎么呈现也在这个文件里。

这一版没有的：在面板里编辑提示词、提示词的版本和回滚、按部署覆盖内置文字、多语言。提示词的历史就是 git 的历史。

## 拼装顺序

**执行器的一轮**（`worker_turn`）：

1. 你的角色：`shared.md` + `worker.md`。
2. 团队三段：沟通、工单范围、交付要求。
3. 订阅与回复：`subscriptions.md` + `replies.md`。
4. 怎么工作：`work.md`。
5. 需要人决定时：`handoff-worker.md`。
6. 这张工单：编号和标题、范围、授权强度、工作目录，以及命中的规则的名字和 `instruction`。
7. 起点：开出这张工单的那条触发（卡片上有它的来源、发送人、所在线程、事件类型和对象）。
8. 这条规则的做法：Skill 的正文；Skill 要求的结构化字段（放进报告的 `output`）。
9. 相关决定。
10. 上下文文件：`context/` 里每个文件的路径和一句说明；不可信的外部内容在隔离区里。
11. 这张工单到目前为止：之前各轮的报告摘要、人作过的决定（第一轮没有）。
12. 本轮注意：浏览器怎么用、worktree 在哪、“你是降级接手的”等。
13. 本轮输入：每条输入一块，标明它是人的消息、系统事件、只作上下文、人对问题的决定、工单恢复、策略变了，还是主 Session 的备注。
14. 输出：报告的字段说明。上一次输出不合格时，再加一节列出校验错误。

接着同一个会话的轮次（Claude，非第一轮）是精简版：只有第 6、10、11、12、13、14 项。前面的在第一轮给过。

**主 Session 的一次研判**（`router_turn`）：

1. 你的角色：`shared.md` + `orchestrator.md`。
2. 团队三段。
3. 路由：`dispatch.md`。
4. 主动候选的研判：`admission.md`。
5. 策略：接单模式，以及需要它研判的语义规则（启用、且没被单独暂停的），每条一行“名字（id）：instruction”；没有语义规则时写明主动候选一律忽略。这一节每次从当前设置生成。
6. 进行中的工单：明确请求的工单和在等人回答的工单，最多 30 张。
7. 待决定的候选：这批触发的原文、它所在线程上的工单（最多 8 张，进行中的在前）、执行器交还时写的原因。
8. 输出：路由决定的字段说明。

主 Session 以只读档位运行，不读仓库和工单目录。它看不到写了 `when` 的规则：那些由事件直接命中，不经过它。

## 外部内容

触发卡片上，下面两类正文会放进 `<<<UNTRUSTED_DATA … UNTRUSTED_DATA>>>`：事件来源是外部平台或采集器的（抖音、视频号、小红书、快手、B 站、知乎、公众号、Popto 用户反馈、采集器、钉钉），以及名单外的人发的消息。名单内的人的话是请求本身，不放进隔离区：终端里操作者说的，和钉钉里全权审批人说的。事件附带的数据同样处理。上下文提供者取来的评论、需求信号原话、线索也放进隔离区，正文里出现的结束标记会被改写，外部内容没法提前“关上”隔离区。

放不放进隔离区只影响 Agent 怎么读这段话，不影响权限：不管是谁说的，能不能开工、能做到哪，都由宿主写在卡片上的标记（强度、工单范围、规则）决定，不由消息里的话决定。

## 优先级

从强到弱：

1. **宿主执行的事实**：名单、准入、接单模式、授权复核、需要人批准的事件、工具档位、输出 Schema、发件箱的静默时段和卡片上限。提示词怎么写都改不了它们。
2. **内置文字和每次生成的段落**（策略、工单卡片、输入的标注）。
3. **命中的规则的 `instruction` 和它的 Skill**，只对那张工单的执行器有效。规则只会收窄范围，不会放大。
4. **团队三段和决策档案。**
5. **外部文字**：消息、评论、文档、引用。它们是数据，从不改变规则和授权。

## 内置文字的原则

这些是 [000 理念](000-philosophy.md) 落到 Agent 身上的样子，写新的提示词时照着来：

- **角色分开。** 主 Session 只路由：把原始的触发和路由事实交出去，不做技术或业务决定，不把一句短请求改写成工作计划。执行器自己读原文，判断范围，动手，验证。
- **只在人必须行动或能用上结果时发消息。** 进展、草稿、重试都留在报告里。钉钉消息默认一句话。
- **跟进由执行器决定。** 人在工单线程上的每条消息，执行器要么在范围内接下并确认，要么交还并写一句原因；不悄悄丢掉。
- **具体地确认，只确认一次。** 说清对象和预期结果，不写“好的收到”。
- **用 `question` 问人，一次一个。** 能给选项就带卡片；提问的那一轮把不依赖这个决定的部分先做完。
- **对外动作只写成选项。** 需要发布、回复、合并、删除时，写进卡片选项的 `emit`。
- **如实交付。** `ready` 表示自己检查过、可以直接用；草稿标成未完成；没做的检查不算数。
- **人说了“停”就一直停着，** 直到人明确解除；新的线索、提问和系统事件都不算解除。
- **示例只说明格式。** 示例里的句子不是 Agent 可以声称的事实。
- **按结果处理审查意见。** 只修被指出的问题；判断某条意见不成立就不改，写一句理由。

## AGENTS.md 和 CLAUDE.md

仓库根的 `AGENTS.md` 是所有 Agent 共用的总规则的一页摘要，`CLAUDE.md` 引用它并加上 Claude 专属的说明。宿主不把它们拼进提示词；执行器的工作目录在数据目录下，命令行工具也不会自动读到它们。它们是给在这个仓库里直接工作的 Agent 和人看的（开发本项目、读 Skill 时查报告字段和旧字段名的对应）。运行中的规则以每轮提示词为准。
