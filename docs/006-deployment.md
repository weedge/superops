# 006 部署与运维

这篇讲怎么安装、配置和运行 superops，怎么从旧的 ops 切过来，以及出问题时看哪里。它建立在 [001 领域模型](001-domain.md) 到 [005 面板](005-panel.md) 之上。

## 跑起来的是什么

- **一个进程** `superops run`：来源（定时、流水线、终端、钉钉）、评估、执行器、发件箱、管理 API 和面板都在里面。它按需拉起子进程：Agent 的命令行、确定性脚本、`dws`、专用浏览器。
- **一个数据目录** `~/popto-superops-data/`（`SUPEROPS_DATA` 可改），700 权限，不进 git。
- **本机的凭据**：Agent 命令行各自的登录、`dws` 的钉钉登录、钥匙串里的 TikHub / RedFox / GitLab 密钥、Chrome 里各平台的登录态。superops 自己不保存任何密钥。

执行器以操作者的系统用户运行。工具档位、禁用清单、“Agent 的环境里没有管理 API 的地址和令牌”、“不带宿主令牌发不出需要批准的事件”都是默认的防线，不是安全边界：`workspace` 以上档位的 Agent 可以运行 python，也就可以读操作者能读的文件。要隔离，用一个只放了 Agent 凭据的专用系统账号。

## 前置条件

- macOS（常驻用 launchd，密钥用钥匙串）、Python 3.11 以上、`uv`、git。
- Agent 命令行：`~/claude.sh`、`~/codex.sh`、`~/agy.sh` 三个包装脚本（和终端别名一致，代理各自在脚本里设），以及 `~/.local/bin/claude`、`~/.local/bin/agy`（只读档位绕开包装脚本直调）。路径在 `agents.yaml` 的 `agents`。**2026-11-12 起 Antigravity（agy）不可用**：已从全部降级链摘掉，原来指定它的 4 条规则（视频质检、社媒监听浏览器补位、GEO 检查、行业爆款拆解）改成 Codex；视频类由宿主先抽帧和转写再交给 Codex；行业爆款拆解要调 Popto 接口，规则上加了 `run.network: true`（Codex 的 workspace 档默认断网）。agy 恢复后把它加回 `fallback_chains` 和这几条规则即可。
- 按用到的功能：`dws`（钉钉）、`ffmpeg` 和 `whisper-cli`（视频质检降级时抽帧转写）、本机 Chrome（自动发布、读创作者后台、专用浏览器）、Node.js（专用浏览器的 playwright-cli）。

`superops doctor` 逐项检查这些，并报告策略校验结果、宿主是否在跑、各来源的状态。

## 要提前登录的和要提前放好的密钥

发布和采集要用登录态，采集和 CI 要用密钥。它们不属于“装好就有”的前置条件，而是要人做一次的事（扫码、把密钥放进钥匙串），而且要在放开自动之前做完。

| 要准备的 | 谁用得到 | 怎么准备 | 放在哪 |
| --- | --- | --- | --- |
| 抖音 / 视频号 / 小红书创作者后台登录 | 执行已批准的发布（自动发布、试运行、存草稿）；到点的指标快照和手动采集（读创作者后台，复用同一份登录态）；线索跟进并发评论（抖音） | `superops publish login douyin`（`wechat_channels`、`xiaohongshu` 同理）：打开有界面的 Chrome，人扫码 | `~/popto-superops-data/browser-profiles/<平台>/` |
| Agent 专用浏览器登录 | 社媒监听的浏览器补位（知乎、B站、搜狗微信）、GEO 检查 | `superops browse install`，再 `superops browse login`（建议用专门的小号） | `~/popto-superops-data/browser-profiles/agent-browse/` |
| TikHub 密钥 | 社媒监听（接口：搜作品、按人群词找人、补粉丝数）；评论采集；抖音指标读不到后台时的兜底 | `security add-generic-password -s popto-ops/tikhub -a popto-ops -w <key>` | 钥匙串 |
| 飞书本人登录（要用飞书才配） | 飞书来源：轮询运营群、发卡片和结果、单聊 / @我 的自动回复 | `lark-cli auth login`（7 天续一次） | lark-cli 自己保存 |
| GitLab 令牌（机器人账号，api 权限） | 接入了仓库（`ci.projects` 非空）时的 CI 轮询、MR 审查与写回、合并闸门、合并、开发工单的推送和开 MR | `security add-generic-password -s popto-ops/gitlab -a popto-ops -w <token>` | 钥匙串 |
| Agent 命令行已登录（Claude / Codex / Antigravity） | 所有 Agent 执行的规则 | 各自的命令行登录一次；`superops doctor` 看包装脚本在不在 | 各 CLI 自己的目录 |
| `dws` 已登录 | 钉钉来源（收群消息、发卡片） | `dws auth login` | dws 自己的配置 |

登录态和密钥都**不跟着数据目录以外的东西走**：新建数据目录（包括从旧 ops 切过来）后，三个创作者后台和专用浏览器都要重新登录一次；钥匙串的服务名沿用 `popto-ops/<名>`，旧 ops 配过的不用重配。扫码登录只能由人来做，Agent 不会去登录任何站点。

**服务启动后会主动检查并提前告诉你**：每次启动，宿主把上表里“有规则用得到”的逐项查一遍（创作者后台是无界面打开 Chrome 看登录态，每个平台十来秒），没准备好的汇成一条消息发到 home 渠道，写清缺什么、影响哪些规则、一条命令怎么补；同样的缺口一天只提醒一次，全部就绪时不出声。没补上的会一直列在 `superops status` 和面板总览的“系统问题”里。随时可以自己查：

```bash
superops preflight            # 看上一次检查的结果
superops preflight --refresh  # 重新查一遍（补完之后用它复查）
```

用不到的不查也不提醒：平台的发布模式是 `off`、相关规则停用、没接入 CI 仓库时，对应的登录和密钥不会出现在清单里。另外每天 16:30（发布卡片前半小时）还有一次“自动发布登录检查”，发现登录失效会在群里提醒。

检查的实现在 `superops/app/preflight.py`：`static_checks`（密钥、命令、专用浏览器，立刻查完）和 `login_checks`（创作者后台，要开浏览器）。结果存在库里（kv `preflight`），`GET /api/preflight` 读它，带 `refresh=1` 重查。要让新的登录或密钥也被提前检查，在这个文件里加一项，并在 `KEY_RULES` / `PUBLISH_RULES` / `BROWSER_RULES` 里写上哪些规则用得到它。

## 安装

```bash
cd dsh-superagent-ops
uv sync                    # 需要代理时先 export https_proxy=… http_proxy=…
uv run superops init       # 建数据目录、superops.sqlite、ops.db，生成 local.yaml（从 ~/claude.sh 里读出代理）
uv run superops doctor
uv run pytest -q
```

## 配置文件各管什么

| 文件 | 管什么 | 怎么生效 |
| --- | --- | --- |
| `policy.yaml` | 策略：接单模式的初始值、研判时限、执行位和闲置期限、明确请求的默认执行方式、home 渠道、各来源的开关和收听范围、各来源的名单 / 可回答人 / 准入表、规则 | 走 MR；`superops check` 校验，`superops reload` 生效 |
| `agents.yaml` | 机器层面：管理 API 的地址和令牌、代理、Agent 的启动方式 / 并发 / 续接、降级链、熔断、忙时顺延的等待（`overflow_after`）、用量策略、预算、数据保留期、静默时段、每日卡片上限、问题默认到期、钉钉发消息的身份、专用浏览器、自动发布模式、需求打分 | 重启宿主 |
| `schedules.yaml` | 定时表：每项的类型、`name`（面板上的中文名）、`at` 或 `every`、`max_late`、`requires` | `superops reload` |
| `~/popto-superops-data/local.yaml` | 本机的值：代理、钉钉群 ID、审批人 ID、GitLab 项目和本机仓库路径。同名键深度覆盖上面两个文件：全部键覆盖 `agents.yaml`；`eval`、`executor`、`sources`、`policy`、`home` 五个键覆盖 `policy.yaml` | 覆盖 `policy.yaml` 的部分随 `superops reload` 生效；其余重启。钉钉来源的开关和群列表要重启 |
| `skills/<名字>/SKILL.md` | 各条规则交给 Agent 的工作说明。面板 → Skill 页能看全部 Skill（被哪些规则用、近 30 天工单数和失败数），仓库里的能直接在面板上改，保存前自动存一份旧版本到 `~/popto-superops-data/skill-history/<名字>/`，能在“历史版本”里对比、恢复；`external_skill_dirs` 里的（Popto 产品仓库的）只读。`schema.json` 连着入库代码，不在面板上改 | 下一轮工单生效，不用重启 |
| 库里的运行时开关 | 接单模式、暂停处理、单独暂停的规则 / Agent / 事件来源 | `superops mode`、`superops pause`、`superops resume`，立即生效，重启后保留 |

几点容易踩的：

- 深度覆盖对列表是整体替换。不要在 `local.yaml` 里写 `policy.rules`，它会换掉全部 47 条规则。
- 切过一次接单模式之后，库里的开关优先于 `policy.yaml` 的 `eval.mode`。
- 规则的 `when.match` 必须是合法的正则，`max_rounds`、`credits_per_run` 必须是数字，文件各节的形状不对会被拒绝并保留原来的设置。`superops check` 除了这些，还检查：规则引用的角色有降级链、Agent 存在、Skill 找得到、上下文提供者认识；`tell: always` 的规则不超过 4 条；home 渠道的来源开着；钉钉开着时名单不为空（提醒）；定时项有规则接（提醒）。`superops run` 启动前会跑同样的检查，有错误就不启动。

### 配钉钉

见 README 的“正式启用前要配的”。要点：`home` 指到运营群；`sources.dingtalk` 打开并填 `chats`；`policy.sources.dingtalk.allowed` 填审批人的两种 ID；按需填 `answerers` 和 `rule_chats`。钉钉来源通过 `dws event consume` 的长连接收群消息和卡片回调，另有一个轮询兜底，本机不需要公网入口。

## 飞书

**钉钉和飞书只能二选一**：`sources.dingtalk.enabled` 和 `sources.lark.enabled` 同时为 `true` 时，`superops check` 报错，宿主不启动、`superops reload` 不生效；切换时把另一个关掉，`home` 也改到开着的那个（`{source: lark, thread: home, address: {chat: "oc_xxx"}}`），否则主动工单的结果发不出去。

飞书和钉钉能做的事一样，以**我本人的身份**（`lark-cli --as user`）收发：运营飞书群里一样能提请求（`@兔管家 …`）、回「T12 1」批红、「T12 …」跟进、「记下来：」「需求：」「暂停 / 恢复」；哪边发起的工单，确认、问题和结果回到哪边。单聊我、或在任何飞书群里 @我 的消息交给自动回复（同一个 auto / off 开关、过滤群、限流；面板上显示成“飞书自动回复”）。

**和钉钉不一样：靠轮询。** 飞书的消息事件只能以机器人身份订阅，没有“别人发给我本人”的事件，所以运营群每 15 秒拉一次新消息（`im +chat-messages-list`），单聊和 @我 每 30 秒搜一次（`im +messages-search --chat-type p2p` / `--is-at-me`），比钉钉慢几秒到几十秒。第一次启动从“现在”开始，不回放历史。系统发消息也是用我本人的身份，所以发出的每条消息记下 ID，轮询到就跳过；我自己在飞书里亲手打的「T12 1」照常处理。

**在面板上切换和配置**：设置页最上面的“聊天渠道”：两张卡片（钉钉、飞书）显示当前用哪个、群、审批人、登录状态；可以“切到飞书 / 切到钉钉”（保存后宿主自己重启，约 15 秒，要求宿主是 launchd 起的，否则提示手动重启）、改群（填群 ID，或完全一样且唯一的群名）、增删审批人（只认 ID：飞书 open_id、钉钉 openDingTalkId / userId）。这些改动存在库里的运行时覆盖（`settings-overrides.chat`），叠在 `local.yaml` 上、记进变更历史；`local.yaml` 本身不改，所以以面板为准，想回到文件里的配置就把覆盖清掉（删库里的 `settings-overrides.chat`）。

**配置**（`local.yaml`）：

```yaml
sources:
  lark:
    enabled: true
    chats: ["oc_xxx"]            # 运营飞书群的 chat_id：lark-cli im +chat-search --query <群名> --as user
    poll_seconds: 15
    auto_reply_poll_seconds: 30
policy:
  sources:
    lark:
      allowed: [{id: "ou_xxx", name: "审批人"}]   # 能提请求、能批所有问题的人：飞书 open_id（不认昵称）
```

**2026-11-12 切换记录**：钉钉关掉，飞书打开，群是「测试superops」（`oc_xxx`），`home` 也指向它；切换前的配置备份在 `local.yaml.bak-before-lark-20261112`。实测：`lark-cli im +chat-messages-list` 的时间只到分钟、是本地时间，系统消息（建群提示等）跳过；群里 `@兔管家` 的请求半分钟内开出工单并把确认和结果发回群里。

**登录**：`lark-cli auth login`（本人身份）；用户登录 7 天要续一次，过期后启动检查和来源页会报“飞书本人身份没登录”。测试里绝不调真的 lark-cli。

## 钉钉自动回复

别人**单聊你**、或在**运营群以外的任何群里 @你**，Agent 起草一段回复、以你的身份直接发出（带 AI 角标和“—— <owner_name>的 Agent 自动回复”署名）。运营群里的消息照旧走工单和批红，不在这里回。

- **开关**：面板首页「钉钉自动回复」，`auto` 自动回复 / `off` 不回，默认 `off`；命令行 `superops autoreply [auto|off]`（不带参数看状态和最近记录）。开关存在库里，重启后保留。
- **它说什么**：读 `prompts/auto-reply.md`（规矩）和 `~/popto-superops-data/auto-reply-context.md`（你的近况，自己改，每次都读最新的），再加系统里进行中 / 最近做完的工单标题。只读，不开工单，不做任何动作。
- **不替你做主**：要你答应排期、要权限密钥、私事、投诉等，它不回或只回“转给本人”，同时在运营群转告你。
- **过滤群**：告警群这类群里 @你 不回，也不记。名单在面板「钉钉自动回复」的“过滤群”里增删，命令行 `superops autoreply exclude add <群ID或群名>`、`superops autoreply exclude remove <群ID或群名>`。**优先用群 ID**：填群 ID 会顺手查出群名；填群名会按名字找群 ID（`dws chat +chat-search`，名字完全一样且只有一个才算），找到就按 ID 过滤，找不到就按群名过滤（收到 @ 时查这个群叫什么再比）。`local.yaml` 的 `sources.dingtalk.auto_reply_exclude` 是初始名单，库里还没有名单时用它；面板上改过之后以库里的为准。只管群里的 @，不管单聊。
- **兜底**：同一条消息只回一次；同一会话 1 小时最多 6 条、全天最多 80 条（防两个 Agent 互相回个没完）；同一会话 30 分钟内最多转告你一次；告警机器人、监控这类自动推送不回也不转告（你在原群本来就看得到）；处理暂停时也不回。
- **监听**：`dws event +listen-im --kind all-direct` 和 `--kind at-me` 两条长连接；`sources.dingtalk.auto_reply_listen: false` 可以连监听都不起。

## 自动发布

人在群里批了发布卡片之后，`publishers.<平台>.mode` 是 `live`、`draft` 或 `dry_run` 的平台由浏览器在创作者后台自动填表：标题、正文、话题、封面、AI 生成声明、发布时间（视频号还有原创声明）。

| 模式 | 填完之后 | 人要做什么 |
| --- | --- | --- |
| `live` | 点“发布 / 发表”，登记作品、排好数据采集 | 不用做；失败或要验证时群里会提醒 |
| `draft` | 点平台的存草稿按钮（视频号“保存草稿”，抖音、小红书“暂存离开”），**不发布**；不设定时 | 到草稿箱检查后自己点发布，发完回 `已发 <发布包ID>` 补登记 |
| `dry_run` | 停在“发布”前截图发到群里，不存不发 | 按群里的说明手动发 |
| `off` | 不开浏览器，把素材和文案推到群里 | 手动发 |

草稿存在哪（2026-11-11 实测）：

| 平台 | 草稿在哪 | 怎么打开 |
| --- | --- | --- |
| 视频号 | 平台上（任何浏览器、任何电脑都看得到） | 视频号助手 → 内容管理 → 草稿箱 |
| 小红书 | **只在本机专用 Chrome 的本地存储里**（页面写着“草稿存储于当前使用的浏览器本地”），手机 App 看不到；最多 100 篇 | 这台 Mac 上 `superops publish open xiaohongshu` |
| 抖音 | **只在本机专用 Chrome 的本地存储里**，而且**只有一个位置**（发布页顶部“你还有上次未发布的视频，是否继续编辑”） | 这台 Mac 上 `superops publish open douyin`，点“继续编辑” |

抖音只能暂存一条：上一条还没发时再来一条，不会覆盖，而是转人工并在群里说明。卡片上全是 `draft` 平台时，批准按钮叫“全部存草稿”。标了 `is_test` 的发布包最多试运行。单独试一条：`superops publish try <发布包ID> --draft`。

**视频号原创声明**：默认在表单里勾“声明原创”（同意原创声明须知后确认），卡片上会写“声明原创”。转载、第三方解读等不是自己原创的，发布包里该平台写 `declare_original: false`。

**发布时间**按发布包 `meta.json` 里该平台的 `scheduled_at`（卡片上“抖音 · 20:00”那一栏）：

| 情况 | 怎么发 |
| --- | --- |
| 批准时离计划时间还来得及 | 用平台的“定时发布”定在计划的那一刻，由平台到点发出 |
| 计划时间在将来，但不够平台要求的提前量（抖音 2 小时，小红书、视频号 1 小时） | 定在平台允许的最早时间：比计划晚一点，不会比计划早 |
| 计划时间已过，或不足 30 分钟 | 立即发布 |
| 发布包里该平台写了 `publish_timing: "immediate"`，或没写 `scheduled_at` | 立即发布 |
| 计划时间超过 14 天 | 报错转人工（平台不支持） |

定时没设置成功（页面改版、时间不可选）时不会悄悄变成立即发布，而是报错转人工。定时发布的帖子按平台实际发出的时刻登记，数据快照（1 小时 / 24 小时 / 72 小时 / 7 天）也从那一刻算起。卡片的备注栏会写明每条是“定时发布 11-12 20:00”还是“立即发布”（按出卡片时估的，批得越晚越可能顺延或变成立即）。

各平台的差别：

- **抖音**：竖封面之外还会设置 4:3 的横封面，不设发文助手会提示“横封面缺失”。发布包有 `media.cover_horizontal` 就用它，没有就从竖封面里裁出内容最多的一块。
- **视频号**：只收 H.264 / H.265 的 MP4，别的编码（如 AV1）上传前自动转成 H.264（要本机有 `ffmpeg`）。
- **小红书**：封面用视频第一帧。

**大视频**：上传要几分钟。三个平台都等视频真正传完（进度、“取消上传”、“上传中”都消失）才点发布；抖音还要等传完才去设封面（没传完就打开封面弹窗，点了“完成”弹窗关不掉，11-11 讲解片传到 98% 时实测）；抖音点完“发布”跳到作品管理页后，还会在后台接着传（右下角“作品上传中，请勿关闭页面”），要等这个提示消失才算发出、才关浏览器，最多等 20 分钟。抖音发布接口没返回作品 ID 时，到作品列表里按标题确认这条真的在。

**平台要身份验证**：点了发布之后，抖音有时要短信验证码，小红书有时要用 App 扫码。无人值守时这条转人工，群里收到“要身份验证”的提醒，**还没有发出去**。要继续自动发，在这台 Mac 上运行：

```bash
superops publish retry <发布包ID> --headed
```

它用原来的批准（24 小时内有效，不用重新批）打开有界面的 Chrome，重新填好并点发布；弹出验证时你在窗口里输入验证码或用 App 扫码（最多等 10 分钟，二维码过期点一下刷新），验证完它接着发、登记作品。只有转了人工、还没发出去的才能重试，已经发出去的不会重发。

发布器是对着真实页面写的（`superops/biz/executors/publishers/`，每个文件开头记着页面要点），平台改版后要重新对一遍。改完用测试包试运行验证：`superops publish try <发布包 ID>`（只填表不发布；加 `--headed` 能看着浏览器操作），或 `superops publish try <发布包 ID> --draft`（填好后真的存一份草稿）。

**测试会留下草稿，测完要清掉。** 试运行虽然不点发布，但视频已经传上去、表单已经填了：小红书离开页面时会自动存一份本地草稿（标题是“暂无笔记标题”或填好的标题），`--draft` 更是每次存一份。留着的话，以后容易把测试草稿当成待发的内容发出去；抖音只有一个暂存位，被测试片占着时下一条真正的草稿会被拒绝。各平台怎么删：

| 平台 | 在哪删 | 怎么删 |
| --- | --- | --- |
| 小红书 | `superops publish open xiaohongshu` → 草稿箱 | 每条右侧“删除”→ 弹出小气泡“草稿删除后不可找回”→ 点红色“删除”。这个 Chrome 只给自动化用，里面的草稿都是自动化留下的 |
| 视频号 | 视频号助手 → 内容管理 → 草稿箱（任何浏览器） | 鼠标移到那一行，右侧出现垃圾桶 → 弹窗“删除草稿”→ 确定。这里也有人手存的草稿，只删测试的（看保存时间和标题） |
| 抖音 | `superops publish open douyin` → 发布页顶部“你还有上次未发布的视频” | 点“放弃”。放弃前确认里面是测试片 |

2026-11-11 测试完已经清过一次：小红书 13 条全删、视频号删了 1 条 30 秒片子、抖音放弃了讲解片的暂存。

## 指标采集

发布成功后自动登记作品，按发布后 1 小时 / 24 小时 / 72 小时 / 7 天各采一次快照（规则 `collect-metrics`，每 30 分钟看一次有没有到点的）。数据从三个平台的创作者后台读，复用发布的登录态；抖音读不到时用 TikHub 兜底。到点超过 12 小时还没采到的节点标成“已跳过”，不再补。

**手动采集。** 想现在就看数据，不用等节点：

| 在哪 | 怎么做 | 采哪些 |
| --- | --- | --- |
| 面板 → 业务 → 数据回收 | 点“立即采集全部…” | 最近 30 天发布、没标记删除的全部作品 |
| 同一张表的每一行 | 点这一行的“采集” | 只采这一条 |
| 终端 | `superops metrics collect`，或 `superops metrics collect <作品ID> …` | 不带 ID 是全部，带了就采这几条（作品 ID 是 `posts.id`，形如 `douyin_7706857639103286538`） |

点了以后会开一张“手动采集指标”工单（规则 `collect-metrics-now`，不往群里发消息），在后台打开各平台创作者后台读数，三个平台一般一两分钟采完；结果在工单的摘要里，表格的“最近一次”列也会更新。手动采的快照记成“手动”，**不占** 1 小时…7 天的节点，也不参与异常判断，所以随时可以点，不会把节点数据搞乱。它跟定时采集共用浏览器，撞上了会等对方用完。它和定时采集一样按规则接单，接单模式不是 `auto` 时不会执行（`observe` 只记一条“本来会接单”）。

**作品在平台上删掉了**，要告诉系统，不然剩下的节点会一直报“后台没找到”：`superops metrics removed <作品ID> …`。标记后剩下没采的节点改成“已跳过”，手动“全部采”也不再包括它，面板上这一行标“已删除”。发布记录本身保留。2026-11-12 已把 11-11 的 30 秒成片（三个平台都删了）标记删除。

**作品 ID 对不上时。** 从草稿箱重新发表、或删了重发，平台会给一个新的作品 ID，系统里登记的还是旧的，采集会报“作品列表里没找到这条”。到创作者后台确认新的那条，再把 `posts` 和 `metric_jobs` 里的作品 ID 改过去（先备份 `ops.db`）。2026-11-11 讲解片的视频号就是这样：18:23 那条后来不在了，20:04 同名的一条才是线上的，已改指过去。

## 开发与合并

需求被批准后，开发工单写 PRD → 人批 → 在独立 worktree 里开发、commit → 宿主推 `agent/*` 分支、开 MR → Codex 审查 → 合并闸门发合并卡片 → 人批后合并。`ci.auto_merge: false` 时合并都要人批。

**测试需求。** 需求原话里写了【测试】（或 `[测试]`、“这是测试…”）的，入池时打上测试标记，需求标题前补上【测试】。需求 Top 10 卡片、PRD 卡片和 MR 标题都会带【测试】；合并卡片按需求池里关联的需求生成，测试需求的标题是“【测试】合并 …？”，建议改成“先不合（这是测试需求）”，风险第一条写明（原话里有“不合并”时直接说出来），理由里附需求原话。测试需求即使打开了 `ci.auto_merge` 也不会自动合并。只是普通地提到“测试”（比如“A/B 测试需求”）不算。

**合并后核实线上版本。** 每次合并（卡片合并、自动合并、别人在 GitLab 上直接合并 Agent 的 MR）都会登记一条待核实：

| 情况 | 怎么处理 |
| --- | --- |
| `local.yaml` 的 `ci.verify` 配了这个项目的线上版本地址 | 每 30 分钟的 MR 轮询顺带去取一次。线上就是这个提交，或线上的提交包含它（后面又合了别的一起上线），记“已上线”（`deploy.verified`，进日报）。过了期限（`within`，默认 24 小时）还不是，发 P0 告警（`deploy.mismatch`） |
| 没配 | 合并时在群里说一句“已合并，但没法自动核实是否上线”（`deploy.unverifiable`），请人上线后自己确认 |

```yaml
ci:
  verify:
    group/popto: {url: https://<线上域名>/version.json, within: 24h}
```

线上版本地址要返回提交号：JSON 的 `commit` / `sha` / `version` 字段，或者纯文本。popto 前端目前构建产物里没有 `version.json`（`popto.cn/version.json` 是 404），所以还没配，合并后都会请人确认上线；要自动核实，得先让前端构建时写出 `version.json`（带 git 提交号）并随产物发布。核实记录在 `ops.db` 的 `deploy_checks` 表。手动核实一次：`uv run python -m superops.biz.ci verify <线上版本地址> <提交号>`。

2026-11-12 用测试需求把这条路完整走了一遍（T70 入池 → T71 周报卡片 → T72 PRD 和开发 → T73 审查 → T75 合并卡片 → T76 合并，popto!13）。当时测试标记没带到卡片上、MR 链接也没写回需求，都已修好；popto!13 已补登记为“没配地址，未自动核实”。

## 启动与停止

前台：

```bash
uv run superops run        # Ctrl-C 停止；-v 打开调试日志
uv run superops run --once # 调试：处理完手头的就退出，不起管理 API
```

常驻（launchd）：

```bash
uv run superops launchd install --print   # 只看会生成什么
uv run superops launchd install           # 写 ~/Library/LaunchAgents/cn.popto.superops.plist
uv run superops launchd install --load    # 写并加载；开机自启，退出后自动拉起
launchctl bootout gui/$(id -u)/cn.popto.superops        # 停
launchctl kickstart -k gui/$(id -u)/cn.popto.superops   # 重启
```

日志在 `~/popto-superops-data/logs/superops.out.log` 和 `superops.err.log`。launchd 不加载 shell 的别名和环境，plist 里写的是绝对路径和 `agents.yaml` 的 `path`。

重启对工作的影响见 003：还在执行中的派工带着恢复说明重新开始，等待的输入和没发出的消息都在库里。想在不停进程的情况下让它安静下来，用 `superops pause`。

管理 API 默认只监听 `127.0.0.1:8797`。要从别的机器访问，在 `local.yaml` 设 `hub.host` 和 `hub.token`；非本机的请求要带 `X-Ops-Token` 或 `Authorization: Bearer`。

## 从旧 ops 切换

两套系统互不依赖：端口（8787 / 8797）、数据目录（`~/popto-ops-data/` / `~/popto-superops-data/`）、launchd 标签（`cn.popto.ops.*` / `cn.popto.superops`）都不同。但它们用同一批对外的东西：同一个钉钉群、同一批平台账号、同一个 GitLab、钥匙串里同名的密钥。并行期间要保证对外动作只有一套在做。

建议的步骤：

1. **装好，不接钉钉。** `superops init`、`doctor`，保持默认的 `home: {source: cli}`。旧 ops 照常跑。
2. **影子运行。** `superops run` 以 `observe` 模式启动。定时触发会照常产生，每条命中规则的记为“本来会接单”；`superops decisions --kind would_accept` 对照旧系统同一时段的 `opsctl tasks`。要知道的局限：`observe` 下采集和 Agent 都不跑，所以由它们产生的下游事件（评论批次、数据异常、脚本送审）不会出现；可以用 `superops emit <类型> --source <来源> --subject <对象>` 手工发几条，看它们会命中哪条规则（需要人批准的事件类型手工发不进来，会记为过滤）。`observe` 不拦人批准的动作：这期间如果在 superops 的卡片上批了发布，它会真的执行。
3. **用明确请求试真实的 Agent。** `superops ask "……"` 在任何模式下都会走完“主 Session 路由 → 工单 → 执行器 → 回话”，结果在 `superops inbox`。这一步验证三个 Agent 的命令行、代理和工具档位在这台机器上是通的。
4. **两套可以同听一个群，但各管各的。** superops 的钉钉来源只认 `T` 开头的编号，`C12 1` 留给旧 ops，卡片不会串。要注意的是不带编号的指令：「记下来：…」「需求：…」「已发 pk_xx」「暂停 …」两边都会各自处理一遍（各记各的决策档案、各进各的需求池、各自回一条回执）。不想要这份重复，并行期间让 superops 先听一个单独的测试群。
5. **切换。** 挑一个旧系统没有待批卡片的时候：
   - 停掉旧的三个常驻进程：`launchctl bootout gui/$(id -u)/cn.popto.ops.hub`，以及 `…ops.opsd`、`…ops.dingtalk-events`。
   - 在 `local.yaml` 配好钉钉和 CI，`superops check`。
   - `superops launchd install --load`，`superops mode auto`。
6. **回退。** `superops mode observe`（或 `superops pause`），停掉 superops，再把旧的三个进程加载回来。

关于数据：

- **`ops.db`（业务库）结构和旧的完全相同，但两套各用各的文件。** 没有迁移工具。想带着历史的内容、作品、指标、需求、线索过来，在两边都停着的时候把旧文件复制成 `~/popto-superops-data/ops.db`（例如 `sqlite3 ~/popto-ops-data/ops.db ".backup '<新路径>'"`）。库里记的文件路径（脚本、发布包、PRD）指向旧数据目录的 `runs/`，要一起用就把那些目录也复制过来；不复制的话，旧内容的原稿在新系统里找不到，新产生的不受影响。
- **`hub.db`（事件、任务、卡片）不迁移。** 旧系统里没批的卡片在新系统里不存在，所以要在没有待批卡片时切换。
- **登录态**在各自数据目录的 `browser-profiles/` 下：复制过来，或者重新登录（`superops publish login <平台>`、`superops browse login`）。
- **`decisions.md` / `not-doing.md`** 是各自仓库里的文件。并行期间旧系统新记的条目要手工补到这边。

## 升级

1. 等没有正在跑的轮次（`superops status` 的执行位是 0），或先 `superops pause`。
2. 备份 `~/popto-superops-data/superops.sqlite` 和 `ops.db`。
3. `git pull && uv sync`，`uv run pytest -q`，`uv run superops check`。
4. 重启宿主，`superops status` 看一眼。

启动时发现策略版本和上次不同，进行中的评估会在新版本下重来。库的结构有版本号（目前是 1）：新版本程序写过的库，旧版本程序会拒绝打开，所以回退要用升级前的备份。

## 排障

先看三处：`superops status`（等你处理的、系统问题）、`superops ticket T12`（一张工单的输入、派工、运行、发出的消息）、`superops decisions`（每个决定的原因）。Agent 每一轮的提示词和原始输出在 `~/popto-superops-data/work/<工单短名>/`。

| 现象 | 原因 | 怎么办 |
| --- | --- | --- |
| `superops run` 报“配置有错误，没有启动” | `policy.yaml` / `agents.yaml` / `local.yaml` 没过校验 | 按列出的错误改，`superops check` 再验 |
| 浏览器类工单（监听补位、GEO 检查）卡在某个页面不动 | Agent 在等模型返回、卡死了（2026-11-12 T102：Antigravity 停在搜狗微信 20 多分钟，CPU 为 0） | 现在 10 分钟没有任何动作就自动结束这一轮、换下一个 Agent（`agent_browser.idle_timeout`）。手动处理：`superops stop T12`，再结束残留的 `agy` / `codex` 进程 |
| 重启后面板打不开，日志里有 `Address already in use` | 上一个进程还在等手头的工单收尾，端口没放 | 现在停止时先关端口，新进程绑不上会每 2 秒重试、最多 2 分钟，再不行就退出让 launchd 重启。2026-11-12 之前的版本会卡在“钉钉在监听、面板打不开”的状态：`launchctl kickstart -k gui/$(id -u)/cn.popto.superops`，并结束它留下的子进程 |
| 启动后群里收到“启动检查：N 项还没准备好” | 有规则用得到的登录态或密钥没准备好 | 按消息里每项的“怎么补”做，然后 `superops preflight --refresh` 复查；用不到的功能可以把对应规则停用或把平台的发布模式改成 `off` |
| 群里提示“要身份验证，自动发布停在了验证这一步” | 平台点发布后要短信验证码（抖音）或扫码（小红书） | 在这台 Mac 上 `superops publish retry <发布包ID> --headed`，在弹出的窗口里完成验证 |
| 群里提示“已存草稿”，但找不到草稿 | 小红书、抖音网页版的草稿只存在本机专用 Chrome 里 | `superops publish open xiaohongshu`（或 `douyin`）打开；视频号在视频号助手的草稿箱 |
| 抖音存草稿转了人工：“只能暂存一条” | 上一条暂存的还没发 | `superops publish open douyin`，把上一条发掉或放弃，再 `superops publish retry <发布包ID>` |
| 飞书来源报错 / 飞书里说话没反应 | 本人身份登录过期（7 天）；`sources.lark.chats` 没填或不是 `oc_` 开头；发话的人不在 `policy.sources.lark.allowed`；轮询有十几秒延迟 | `lark-cli auth login` 重新登录，`superops preflight --refresh` 复查；来源页看飞书的状态和最近一次出错 |
| 钉钉自动回复没回 | 开关是 `off`；是运营群里的消息（走工单）；对方只回了“收到”之类；到了限量（同一会话 1 小时 6 条、每天 80 条）；要你本人拿主意（会在运营群转告你）；处理被暂停 | `superops autoreply` 看最近记录，每条写着“已回 / 没回 / 到上限”和原因 |
| 发布转了人工、群里提示“登录失效” | 创作者后台的登录过期了，或者换了数据目录后还没登录 | `superops publish login <平台>` 重新扫码；`superops preflight --refresh` 确认 |
| 命令报“宿主没有运行” | 进程没起来，或 `hub.port` 和运行中的不一致 | 看 `logs/superops.err.log`；`superops run` 前台起一次看报错 |
| 定时到点了什么都没发生 | 接单模式是 `observe`（只记录）或 `off`；处理被暂停；规则被暂停；定时项的 `requires` 指的配置是空的；这个定时是装机后第一次见，从下一次开始 | `superops decisions` 看那条决定的原因；`superops fire <cron.类型>` 手动补发 |
| 事件进来了没开工单 | 决定的原因会写明：本来会接单 / 没有命中已启用的规则 / 规则已暂停 / 同线程上的工单还在进行（事件已送达它）/ 到了轮数上限 / 超预算 | 按原因处理；误判的规则改 `when` |
| 触发显示“被来源过滤” | `needs_approval`：Agent 想发需要人批准的事件；`origin_paused`：这个事件来源被暂停了；`source_off`：来源关着；`chat_not_listened`：钉钉群不在收听范围 | 第一种是预期行为；其余按需恢复或改配置 |
| 在群里 @兔管家 没反应 | 发送人不在名单上（留底为忽略，不回话）；群不在 `chats` 里；钉钉来源没开；长连接断了（来源页显示出错） | `superops triggers --source dingtalk` 看有没有收到、去向是什么 |
| 回 `T12 1` 收到“没有权限” | 发送人的 ID 不在 `allowed`，也不在这条规则的 `answerers` | 把 `openDingTalkId` 和 `userId` 都填上，`superops reload` |
| 回 `T12 1` 没批成，提示需要原因 | 选项标了 `require_reason` | `T12 2 原因` |
| 卡片迟迟没发出来 | 静默时段（非 P0 等到早上）；当天卡片到了上限（顺延）；处理被暂停；钉钉发送失败在重试 | `superops ticket T12` 的“发出的消息”看状态；系统问题里有没有“发消息连续失败” |
| 工单一直“排队中” | 执行位满了；规则在等 `after` 的前置工单；处理被暂停 | `superops status` 看执行位 |
| 工单一直“进行中”但没有运行记录 | 降级链上的 Agent 都在忙、熔断或被暂停，这一轮在排队 | `superops agents` 看状态；`superops agents reset <名>` 解除熔断 |
| 工单失败：“可用的 Agent 都没能完成这一轮” | 每个 Agent 都试过且失败 | 看 `superops ticket T12` 的运行记录和工单目录里那一轮的 `.stderr`；修好后 `superops retry T12` |
| Agent 熔断，类型是认证 | 命令行的登录过期 | 在终端里重新登录那个 CLI，再 `superops agents reset <名>` |
| 开发工单失败：“开发环境没准备好” | `ci.repos` 没有这个项目的本机路径；不知道在哪个仓库（事件没带项目，`ci.projects` 不止一个）；worktree 里有未提交的改动 | 补配置或清理 worktree，`superops retry` |
| 浏览器工单失败：“专用浏览器没开起来” | playwright-cli 没装，或登录态目录没初始化 | `superops browse check`，按提示 `install` / `login` |
| 系统问题：“研判没有完成” | 主 Session 的 Agent 不可用或超时；它的决定被宿主拒绝 | `superops reevaluate <trigger_id>`；确认不需要处理就 `superops dismiss <decision_id>` |
| 改了 `policy.yaml` 没生效 | 没 `reload`；改的是 `eval.mode` 而库里已有开关；改的是 `agents.yaml`（要重启） | 对应处理 |
| 启动报“数据库是更新的版本” | 程序版本比写这个库的版本旧 | 换回新程序，或用升级前的备份 |
| `superops emit` 发的事件显示“被来源过滤：这类事件要人批准后才能发” | 这个事件类型有 `requires_approval` 的规则在接，只有人在卡片上选中的选项、或宿主拉起的确定性脚本才发得出来 | 预期行为。要执行那个动作，去回答对应的卡片 |
| 批了卡片，回执说“发出 N 个已批准的动作”，但没有开出工单 | 已批准的事件不受接单模式限制，但接它的规则被暂停、到了轮数上限或超了预算 | `superops decisions` 看那条决定的原因 |
| 给已完成的脚本工单回了一句话，它又“已完成”了一次，什么都没做 | 脚本工单不因为人的消息重跑；这句话被交还去评估 | 要重跑：失败的用 `superops retry`，已完成的重新发它的触发 |

## 数据保留

每天 04:30 的定时触发“数据保留清理”规则，它运行 `superops retention`；`uv run superops retention --dry-run` 先看会动什么。保留期在 `agents.yaml` 的 `retention`，两个天数的上限都是 170。

| 数据 | 保留 | 到期怎么处理 |
| --- | --- | --- |
| 工单目录 `work/`、脚本运行目录 `runs/`、发布截图、WorkBuddy 收发件箱 | `runs_days`，默认 90 天；还在用的不动 | 删除。`ops.db` 还引用着的文件（脚本、发布包、PRD）先挪到 `content/_archived_work/` 或 `content/_archived_runs/`，引用路径一并改 |
| `superops.sqlite` 里的正文：触发的正文和事件数据、已结束工单的输入与报告正文、已结清消息的正文 | `text_days`，默认 170 天 | 清空正文。编号、类型、状态、时间、谁批的这些元数据永久保留 |
| `ops.db` 里需求信号的原话 | `text_days` | 清空 |
| 评论原文 | 180 天 | 评论采集每小时删一次，清理任务每天兜底 |
| 日志 | 超过 `log_max_mb`（20 MB）轮转 | 保留 `log_keep`（2）份旧的，旧的先打码 |

170 比 180 少 10 天，是因为周报会引用上一周的评论：留出余量，保证评论原文的所有副本都在 180 天内删掉。

清理任务还会补扫没打过码的工单目录和运行目录（宿主中途被杀时来不及扫的）。打码规则见 README 的“关键行为”。
