# Popto 产品运营研发多 Agent 系统的整体流程

这篇用业务的眼光把 superops 走一遍：结构、一张工单的一生、四条流水线、你一天会看到什么。概念的定义在 [001 领域模型](001-domain.md)，会话怎么续接在 [009 会话](009-sessions.md)，谁能让工作开始在 [002 授权](002-authorization.md)，一轮怎么跑在 [003 执行](003-execution.md)。

## 一、总体结构

```text
 ┌─ 来源 ─────────────────────────────────────────────────────────────────┐
 │ 定时 schedules.yaml │ 流水线事件（脚本 / 工单 / 人批过的选项）│ 钉钉群 │ 终端 │
 └──────────────┬─────────────────────────────────────────────────────────┘
                ▼ 触发：属于一个线程（一个业务对象一个线程），只存一次
 ┌─ 宿主 superops run（127.0.0.1:8797，superops.sqlite 留底）───────────────┐
 │ ① 订阅扇出：线程上已有工单在跟 → 作为输入送给它                           │
 │ ② 评估：准入（谁可以发起、多强）→ 研判（事件直接命中规则 / 主 Session 路由）│
 │      接单 → 开一张带授权的工单      忽略 / 本来会接单 → 只留底            │
 │ ③ 执行器：每张工单一个目录、一段会话，有输入就跑一轮                      │
 │      Agent：claude.sh → codex.sh → WorkBuddy（按角色的降级链）   │
 │      脚本：采集、登记、发布、回复、合并，不用大模型                       │
 │ ④ 发件箱：唯一找人的出口。静默时段、每天 10 张卡片上限                    │
 └──────────────┬─────────────────────────────────────────────────────────┘
                ▼ 一轮的报告，按内容分几路
   ├─ 业务事件 → 回到流水线来源：命中下一条规则，或送回负责这个对象的工单
   ├─ 问题卡片 T12 → 钉钉群 → 人回「T12 1」→ 宿主发出选项里写好的事件（带批准凭据）
   ├─ 结果 → 明确请求的回到提请求的地方；人批准的动作做完回一条；其余只有日报这类才发，进日报
   └─ 结构化产出 → ops.db（选题、脚本、评论分类、需求、线索）
```

**人只做三件事**：回答卡片；偶尔说一句「记下来：…」「需求：…」「已发 pk_xx 链接」；想让 Agent 做一件规则之外的事时 @兔管家 说一声。其余环节由事件推着往下走。

运营群之外还有一条旁路：**钉钉自动回复**。别人单聊我、或在别的群里 @我，Agent 读我的近况起草一段回复，以我的身份发出（面板首页开关 `auto` / `off`）。它只聊天，不进上面的流程，不开工单、不做任何动作；要我本人拿主意的转告到运营群。

和上一版相比，中间少了两样东西：没有“任务队列”，也没有“每个事件一次性跑完就结束的任务”。一件事从头到尾是**一张工单**，它记得自己为什么可以做（授权）、做到哪了（各轮的报告）、在等什么。

## 二、一张工单的一生

以“写一条内容的脚本”为例。

1. **触发进来。** 人在选题卡片上批准了一条选题，宿主发出 `content.topic.approved`，对象是 `content:c_20261113_01`。它落在这条内容自己的线程上。
2. **评估。** 这条事件带着人的批准凭据，准入给它“明确”的强度：人批了的事在任何接单模式下都做。它命中规则“写脚本”，宿主做几项确定性的检查：规则没被暂停、这个线程上没有这条规则的工单在跑、没超预算。都过，接单。
3. **开工单。** 工单 T31 带着授权：范围是规则的 `instruction`，强度是明确，依据是这条规则、谁在哪张工单上批的、当时的策略版本。它订阅了这条内容的线程，另有一个只属于它的线程 `ticket:T31`：人带着编号说的话落在那里。
4. **第一轮。** 执行器在 `work/t31-script-writing/` 里拉起 Claude：提示词里有工单卡片、Skill、相关决定、选题数据和帮助文档。Claude 写完各平台的脚本，报告里发出 `content.script.ready`（送审），状态 `waiting`。工单进入“等后续事件”。
5. **事件回流。** 送审事件落在同一个线程上。它不回送给 T31 自己；它命中规则“脚本合规复核”，开出 T32，由 Codex 执行（审查者不能是写稿的 Agent）。送审事件没有批准凭据，是推断的：`observe` 模式下这里只记一条“本来会接单”，`auto` 才开出 T32。
6. **订阅把结论送回来。** T32 复核完，发出 `content.compliance.failed` 和逐条问题，自己结束。这条事件在内容的线程上，T31 订阅着这个线程，所以它成为 T31 的输入。T31 跑第二轮：Claude 接着上一轮的会话，在原稿上改，再次送审。
7. **结束。** 第二次复核通过，`content.compliance.passed` 送回 T31，它报告 `ready`，以“已完成”结束。中间的送审、打回、改稿都不出现在群里；结束时 home 渠道会有一条结果，因为这张工单是人批准的选题开出来的，授权是明确的。

出问题时：

| 出了什么事 | 怎么处理 |
| --- | --- |
| Agent 额度或认证错误 | 熔断这个 Agent，这一轮换降级链上的下一个 |
| 超时 | 换下一个；同一 Agent 连续 3 次超时，熔断 30 分钟。浏览器类的工作 10 分钟没有任何动作也按超时提前结束 |
| 输出不合格 | 带着校验错误让同一 Agent 重试 1 次，还不行再换 |
| 决策、开发、审查找不到合适的 Agent | 这一轮排队等，不交给更弱的 Agent |
| 主力 Agent 只是忙 | 先排队，等满 10 分钟才顺延给下一个 |
| Agent 做不下去 | 报告受阻：明确请求和高优先级的通知人，其余进日报；人在这张工单上回一句话，它就接着做 |
| 宿主停止或重启 | 停止时取消正在跑的轮；重启后那一轮带着“先检查已经做了什么”的说明重来 |

每张工单的全部经过用 `superops ticket T31` 看：授权、每一条输入、每一次派工和报告、每次拉起 Agent 的记录、发出的每条消息。

## 三、四条业务流水线

箭头上的事件名就是 `policy.yaml` 里规则的 `when`。标 🔒 的是只有人批过才发得出来的事件。

### ① 内容流水线（周五 15:00 开始）

```text
定时 → 排下周选题（Claude）→ 卡片：选题清单 → 人批
  🔒 content.topic.approved（每条内容一个线程）
→ 写脚本工单（Claude）─ content.script.ready → 合规复核工单（Codex，最多 3 轮）
        ▲                                         │
        └── content.compliance.failed / passed ───┘   复核结论回到写稿的那张工单，在原稿上改
→ 素材制作（批量口播视频，规则已按 D-20261110-01 停用）→ content.media.ready
   图文走另一条路：每天 09:30 今日发布推荐（Claude）：今天已有发布包在走就不出声，没有就从写好稿的图文里挑 → 卡片“今天发哪篇” → 人批
   🔒 content.images.requested → 图文出图（Claude：按稿子逐页排版、用帮助文档截图配图、渲染成 3:4 图片）
   ─ content.images.ready → 图文质检（Codex，不审自己出的图；截图露没露积分 / 账号、文字对不对，最多 3 轮）
        ▲                                         │
        └────── content.images.rework / content.qa.passed ──┘   打回回到出图的那张工单，在原图上改
→ 视频质检（Codex，看抽帧和转写）─ content.qa.passed → 生成发布包（Claude）─ content.pack.ready → 登记入库（脚本）
→ 17:00 定时 → 卡片：今晚待发布 N 条（脚本生成，到期按“全部不发”）→ 人批（可以只批其中几条）
   （17:00 以后才入库、今天要发的发布包——比如上午批了“今天发”、出图拖到傍晚——入库时当场补发一张待发布卡片）
  🔒 content.publish.approved（每个发布包一个线程）
→ 执行发布（脚本）：按各平台的发布模式——
    live   浏览器自动填好并发布：离计划时间还来得及就用平台的“定时发布”，来不及（已过或不足 30 分钟）就立即发布；
           大视频等传完才点发布，平台要短信 / 扫码验证时转人工，`superops publish retry <ID> --headed` 人在窗口里验证后接着发
    draft  浏览器自动填好后存草稿、不发布（2026-11-11 起三个平台都是这个模式），群里说草稿在哪，人检查后自己发
    off    把发布包推给人
→ 自动发布成功直接登记帖子；人发的（包括从草稿发的）回复「已发 pk_xx [链接]」→ 补登记
```

- 写稿自查和合规复核用同一份《内容合规清单》（`skills/ops-compliance-review/checklist.md`，内联进两个 Skill）；产品功能以 Popto 帮助文档为准，开工前复制进 `context/popto-help/`。
- **同一线程上晚到的事件**：同一批事件里晚到几毫秒的，评估时如果规则发现同线程已有进行中的工单，会把事件真正交给它；工单这一轮报 `ready` 时还有没处理的输入，就再跑一轮。2026-11-12 竞品评审批的 10 条需求曾因此丢了 2 条，已修。
- **订阅带来的变化**：上一版里复核打回要发一个“改稿事件”，另开一个改稿任务，再把上一版原稿复制过去。现在没有改稿任务：写稿的工单还在，原稿就在它的目录里，复核结论直接成为它的下一条输入。复核的轮数由规则的 `max_rounds` 管，改稿的轮数由 Skill 写明。
- 素材制作的规则停用期间，视频稿在合规通过之后不会自动往下走；`content.compliance.passed` 只留底。图文稿由每天 09:30 的今日发布推荐（或人问“今天发什么”）发卡片，批了才出图；小红书的发布器会发图文（切到“上传图文”、按页序传图，其余和视频笔记同一个表单），批准发布后按小红书的发布模式执行；别的平台的图文还是转人工（下载图片、复制文案、到官方发布页发）。

### ② 数据回收（发布后自动开始）

```text
social.post.published → 排定采集（脚本）：发布后 1 小时 / 24 小时 / 72 小时 / 7 天各一次快照
每 30 分钟定时 → 采到点的快照（脚本）：读抖音 / 视频号 / 小红书创作者后台，抖音读不到时 TikHub 兜底
人点“立即采集”（面板 / superops metrics collect）→ 手动采集（脚本）：现在就采一份“手动”快照，不占节点
  ├─ social.metrics.snapshot → 只留底
  └─ social.metrics.anomaly（高于中位数 3 倍或低于 0.3 倍）→ 单条复盘（Claude，只读）→ 结论进日报
每小时定时 → 采集评论（脚本）─ social.comment.batch（攒 10 分钟）→ 评论分拣（Claude，只读，不可信输入）
  ├─ 回复草稿 → 卡片 → 人批 → 🔒 social.reply.approved → 回复执行（脚本：把批准的回复整理好推给人去发）
  └─ 需求信号 → 入库进需求池
06:40 导入漏斗数据 → 08:30 日报（等采集类的工单跑完再开始；结果发到群里）
周一 09:00 周报和需求 Top 10
```

日报是少数会把结果发到群里的规则（`tell: always`）。定时和采集起的其余工单，结论都在日报里；人批准的回复执行完也不另外出声（`tell: never`），结果进日报。

### ③ 需求 → 开发

```text
需求信号（评论分拣入库 / 自用摩擦 ops.dogfood.friction / 人说「需求：…」）→ 需求归并（Claude，只读）
周四 10:00 → 竞品数据采集（脚本：按竞品词搜抖音、小红书讨论最多的作品，拉用户评论；满 28 天再采竞品账号）
  → competitor.comments.batch → 竞品评论需求评审（Claude，只读，评论是不可信输入）
      → 评审卡片（候选需求 + 原话 + 来源作品的平台 / 作者 / 标题 / 链接 + Popto 现状）→ 人批（可只批几条）
      → demand.manual → 需求归并（同上）进需求池
  → competitor.data.ready（满 28 天，或手动 superops fire cron.competitor_research）
      → 竞品调研（Claude，网页搜索 + 采到的账号和作品）→ 竞品调研报告（每条附来源）→ 摘要发到群里
周一 → 周报与需求 Top 10（Claude）→ 卡片 → 人批
  🔒 demand.approved（每个需求一个线程）
→ 开发工单（Claude，独立 worktree）：写 PRD → 卡片 → 人批 → 同一张工单接着开发，git commit
→ 宿主推送并开 MR；工单开始跟随这个 MR 的线程
   ─ gitlab.mr.opened / updated → MR 审查工单（Codex，最多 3 轮）─ gitlab.review.done → 写回 MR 评论和标签（脚本）
        ▲                                                             │
        └──────────── gitlab.review.changes_requested ───────────────┘   审查意见回到开发的那张工单，同一个分支接着改
   ─ gitlab.review.passed → 合并闸门（脚本：数据库迁移、计费、鉴权、密钥、改动超过 800 行都要人看）
→ 卡片 → 人批 → 🔒 gitlab.mr.merge_approved → 合并（脚本）─ gitlab.mr.merged
→ MR 的线程关闭，开发工单随之以“已合并”结束
→ 线上核实（每 30 分钟随 MR 轮询）：线上包含这个提交 → deploy.verified 留底；超过期限还没上线 → deploy.mismatch P0 告警；
   仓库没配线上版本地址 → 合并时 deploy.unverifiable 请人确认上线
```

- **订阅带来的变化**：上一版里审查打回，要靠一条“作者修复”规则重新开任务、重新准备 worktree。现在开发工单从 PRD 一直活到 MR 合并：PRD 的批准、审查意见都是它的输入，Claude 接着同一段会话在同一个分支上改。“作者修复”规则只在负责这个 MR 的工单已经不在时才另开一张。MR 线程上的任何事件都会这样送回开发工单，包括流水线失败（`gitlab.pipeline.failed`），不过仓库里目前没有产生这个事件的脚本。
- **测试需求**：原话标了【测试】的需求带着测试标记走完全程，需求卡、PRD 卡、MR 标题、合并卡片都标出来，合并卡片建议“先不合”并附原话，也不会被自动合并。
- 开发工单在 MR 开出后显示为“等你验收”：它在等的是 MR 被合并或关闭。
- 每 30 分钟的 CI 轮询是兜底：人手推到 `agent/*` 分支上的修改最晚 30 分钟被发现并送审。

### ④ 获客

```text
14:00 定时 → 社媒监听·接口（脚本：TikHub 搜抖音 / 小红书 / 视频号 / 快手近 24 小时，按面板上“在用”的意图词）→ 作品入库 mentions
  → social.mention.new → 判断线索（Claude，只读，帖子是不可信输入）→ 线索入库（每条带要评论的作品链接和评论原文）
14:10 定时 → 社媒监听·浏览器补位（Codex，专用浏览器 agent-browse；只搜知乎 / B站 / 搜狗微信；只浏览）→ 线索入库
  → lead.batch.ready → 今日线索卡片（脚本，最多 10 条，明细里就是要发的评论原文，可以只批几条）→ 人批
  → 🔒 lead.comment.approved → 跟进并发评论（脚本：品牌号在作品下发原文，目前只有抖音；发不了的记“待跟进”人去发）→ 结果发到群里
  → lead.followup.approved / dismissed → 登记为“待跟进”或“不跟进”（脚本）；互动由人用品牌号去做
  → 卡片到期 → 按“都不跟进”登记（登记不需要批准，所以到期也能执行；发评论要批准，到期不会发）
周三 10:00 → GEO 检查（Popto 在各家 AI 助手答案里的可见度）
采集到行业热门视频 → 拆解结构（消耗积分，受单日预算限制）→ 进入下一轮选题的参考
```

线索卡片可以配限定的回答人（`answerers: {lead-card: [...]}`）和单独的群（`rule_chats`）：负责跟进线索的人只能批这一类卡片。

### 兜底

- 每周日 10:00 大扫除：要删的东西列成清单请人批，批了才由清理脚本执行。
- 每天 04:30 数据保留清理。
- Popto 线上任务失败：Codex 按 P0 排查，要人处理的立刻告诉人。
- 没有命中任何规则的事件只留底，在决定里写明“没有命中已启用的规则”。

### 还没有发送方的事件

下面这些事件有规则在等，但仓库里没有产生它们的脚本或 Skill，要由外部系统通过管理 API 的 `/v1/events`（或 `superops emit`）发进来才会有（它们都不是需要人批准的类型，谁发都收）：`popto.task.failed`（线上报错排查）、`popto.feedback.new`（用户直接反馈）、`release.note.ready`（上新选题）、`hot.video.new`（行业爆款拆解）、`gitlab.pipeline.failed`、`content.media.ready`（素材就绪；素材制作的规则停用，它的 Skill 也在仓库外）。

## 四、你一天会看到什么

| 时间 | 钉钉群里出现的内容 |
| --- | --- |
| 08:00 | 夜里攒下的消息和卡片（静默时段 22:30–08:00 只发 P0），逐条发出 |
| 08:30 | 日报：昨日数据、异常、待你决定的事、Agent 状态、系统改进建议 |
| 09:30 | 今天还没有能发的内容时：“今天发哪篇图文”卡片（今天已有发布包在走就不出声）；批了自动出图、质检，赶上 17:00 的待发布卡片 |
| 白天 | 零星的问题卡片：评论回复、PRD、MR 合并，每天最多 10 张，超出的顺延到次日；MR 合并后，仓库没配线上版本地址的会说一句“请确认上线” |
| 14:00–14:30 | “今日线索”卡片（接口监听 + 判断线索，粉丝不足的不上卡）；批了“跟进并发评论”的，发完一条结果：发出几条、哪些要你自己去发 |
| 14:10 以后 | 浏览器补位（知乎、B站、搜狗微信）找到线索时，再来一张今日线索卡片 |
| 17:00 | “今晚待发布”卡片；批完后收到“已存草稿”（附草稿在哪）、自动发布的结果，或要你手动发的发布包 |
| 任何时候 | 你 @兔管家 提的请求：一句确认，做完一句结果；自动回复打开时，别人单聊你或 @你 而 Agent 判断要你本人拿主意的，一条“有人找你” |
| 22:30 以后 | 只有 P0：线上故障、部署对不上、Agent 长时间不可用 |

每张卡片是一条带编号的消息，回一行就行：

```text
T42 1              选第 1 个选项
T42 2 这周人手不够  选第 2 个，写上原因
T42 1 3,5          只批明细里的第 3、5 条
T42 标题再短一点    不是选项：作为跟进消息交给这张工单的 Agent
```

回答之后群里有一条回执：选了什么、发出了几个已批准的动作。批准的动作不看接单模式，`observe` 下也会执行。卡片到期没人处理，就按卡片上写好的安全选项处理，这个选项不会触发任何需要批准的动作，群里同样有一条回执（“登记了 N 项（不做对外动作）”）。卡片上的到期时间是东八区的时间。

编号只认 `T` 开头的；`C12` 是旧 ops 的卡片。给一张已经完成的脚本工单（发布、登记这类）回话不会让它重跑：这句话会被当作一条新的请求去评估。

Agent 干活的过程不出现在群里。想知道一张工单现在怎样，开面板或 `superops ticket T42`。

## 五、怎么看运行情况

- `superops status`：等你处理的工单、系统问题、过去 24 小时的流量、执行位、不可用的 Agent。
- `superops tickets --filter person|open|idle|ended`：工单列表；`superops ticket T42`：一张工单的来龙去脉。
- `superops decisions`：每条触发最后是什么决定、为什么；`--kind would_accept` 看 `observe` 模式下“本来会接”的。
- `superops triggers`：最近进来的触发和它们的去向。
- 面板（`superops panel`，和管理 API 同址）：同样的内容，实时刷新，另有一页业务统计。见 005。
- `superops digest`：一段时间的留底摘要，日报用的就是它。

## 六、敏感信息与数据保留

- **打码**：Cookie、Authorization、各类 token / 密钥（含钥匙串里的原值）、手机号不进日志和输出。三处把关：专用浏览器每条命令的输出和页面快照先打码再交给 Agent；Agent 每一轮结束，宿主把工单目录扫一遍，报告入库、回传之前再打一遍；数据保留清理每天补扫没打过码的目录。
- **不可信输入**：评论、帖子、网页、名单外的人的群消息在提示词里放进隔离区，处理它们的规则用只读档位。它们里面的“指令”改不了规则、名单和授权。
- **保留期**（`agents.yaml` 的 `retention`，每天 04:30 执行；`superops retention --dry-run` 先看会动什么）：工单目录、脚本运行目录、发布截图保留 90 天，内容库还引用的文件先归档；状态库里的正文 170 天后清空，元数据永久保留；评论原文 180 天删除；日志超过 20 MB 轮转。细节见 006。
