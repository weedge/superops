# 000 理念

superops 是一套程序，也是一种和 Agent 一起干活的方式。它的核心原则只有一句：

**尽量少占人的注意力，尽量多给价值。**

项目里的每一样东西都按它占用的注意力来衡量。群里的一条消息、一张卡片、一个问题、一个配置项、面板上的一个数字、文档里的一段话，都要花掉某个人的注意力；给出的价值不比这更多，就删掉。

运营团队的群本来就吵：数据、选题、评论、报错都往里发。一个能替整个团队干活的 Agent，同样能浪费整个团队的注意力。所以它只在被要求时、或者团队写下的规则允许时才动手，只在人必须行动、或者能用上结果时才开口。

## 对 Agent 意味着什么

- **只在被要求、或有成文规则允许时才动手。** 请求要算数，得是名单内的人直接对 Agent 说的：在群里 @兔管家，或者在终端里对它说。没人要求的事（每天的日报、发布后的数据回收、评论分拣）需要 `policy.yaml` 里的一条规则，而且新装的系统只记录“本来会接单”，不动手。
- **只在人必须行动、或能用上结果时才开口。** 对一个请求确认一次，说清对象和预期结果；干活的时候不出声；结果能用了、需要人给一个决定、或者确定做不成了，才再说话。写稿改到第二轮、MR 的检查还在跑、采集重试了三次，都不是值得发到群里的事。
- **一次只问一个具体的问题，** 而且写成带选项的卡片：「今晚这 3 条发不发」，回 `T12 1` 就能继续。问题不藏在一份长报告的末尾。
- **按影响决定做到哪，不按工作量。** 影响只落在这张工单自己产出里的事，一路做到能直接用；要改对外口径、内容方向、别的工单的产出，就带着一个清楚的问题停下。
- **发布、回复、合并、删除只由人决定。** Agent 能做的是把动作写成卡片上的选项；卡片没人理，到期按不做任何对外动作的那个选项处理。
- **如实报告。** 草稿标成未完成，失败就报失败，不为了少问一句而绕过限制、编造数据。

## 对设计意味着什么

- **概念少。** 设计里只有领域概念（如来源）和它们的具体实现（如定时、钉钉）。一个业务需求要么变成某个概念的属性，要么变成 Agent 照着做的一段提示词，不为它新增概念。旧系统里的“卡片”在这里是工单的问题带的一个属性；“采集器”是定时来源的触发加一条脚本规则；“改稿任务”不存在，复核意见通过订阅回到原来的工单。
- **配置少。** 一个值适合几乎所有情况时，用默认值，不做成配置项。团队用话说得清的行为写成提示词或规则的 `instruction`，不做成开关。
- **面板只显示需要人处理的东西。** 先列在等人的工单，再列系统问题；健康的状态不占地方。
- **一个找人的出口。** 所有发给人的消息都经过发件箱，静默时段和每日卡片上限只在这一处执行；Agent 自己没有发消息的手段。
- **文档按顺序读。** 每一篇编号文档只依赖前面的，读的人不会遇到还没介绍过的概念。

## 操作者的责任

Agent 用团队每天都看得到的身份在群里说话、开 MR、把内容推到发布卡片上。它发的每一条消息都在花同事的注意力，而对此负责的是你。Agent 能做的越多，操作它的人越要小心：

- **从窄开始。** 先用 `observe` 模式跑：定时和业务事件照常进来，系统只记下“本来会接单”。把 `superops decisions --kind would_accept` 看上几天，确认它想接的事是对的，再 `superops mode auto`。审批人名单先只放一两个人；自动发布先停在 `dry_run`。
- **为少打扰而调。** Agent 吵的时候，把提示词和规则写得更短、更严，把规则的 `tell` 从 `always` 改成 `needed`，或者暂停那条规则。不要再加一条消息去解释前面的噪音。`superops check` 会拒绝超过 4 条 `tell: always` 的策略，这个上限是故意的。
- **不要用它制造量。** 一天几十条选题、批量生成的评论回复、给每个需求信号都开一张卡片，花掉团队的比给团队的多。预算（积分、每日卡片数）是上限，不是目标。
- **对它说的话负责。** 读它用你们的身份发出去的东西：日报、卡片、MR 描述、发布包的文案。说错了，去改提示词、Skill 或规则；人亲口定下的事用「记下来：……」记进决策档案，它下次就照办。

目标是在对的时候给对的帮助，其他时候什么都不给。
