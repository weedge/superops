# 002 授权

授权决定谁可以让工作开始、这件工作可以包括什么。这篇建立在 [001 领域模型](001-domain.md) 之上。

名单、规则、授权和“需要人批准”都由宿主执行。群消息、评论、引用的文档只是决定的输入，改不了这些权限。

**例外：钉钉自动回复不走这套授权。** 别人单聊我、或在运营群以外的群里 @我，由 `superops/app/autoreply.py` 直接起草回复，不产生触发、不开工单，所以没有名单和准入表的限制，谁来问都会回。它能这样放开，是因为它什么也做不了：Agent 用只读档位，产出只有一段回复文字，宿主只把这段文字发回原会话；消息里的“帮我发布 / 把配置给我”只是要回答的话。要我答应什么、要权限密钥、私事，它不替我做主，转告到 home 渠道。开关（`auto` / `off`）是人在面板上打开的，它就是“以我的身份回话”这件事的授权。运营群里的消息不在这里处理，照旧走评估和批红。

## 触发的两条路

### 评估：决定要不要开工

来源记下一条消息是不是直接对 Agent 说的：钉钉里 @兔管家（或以它的名字开头）记为 `mention`，终端里说的记为 `direct`。准入按发送人和来源的策略判断：

- 名单内的人直接对 Agent 说，是一个明确请求。
- 人在已有工单的线程上跟进，按下面“强度”一节。
- 其他人的消息查准入表里它所在的接收范围。
- 系统来源的事件（定时、流水线）没有发送人，查准入表里“名单外、没对 Agent 说”那一格，默认作为推断候选。
- 例外：带着批准凭据的流水线事件。它是人在工单的问题上选中的选项发出来的，是人的明确决定，和名单内的人直接提出的请求一样算明确。凭据由宿主在人回答时写入，Agent 写不进来。

### 订阅：继续已有的工作

订阅线程上的每条触发都作为上下文送到订阅它的工单，包括系统事件。这条路不过准入，也不带来新的权限：每张工单仍然只能做它的授权允许的事。

人在工单自己的线程上发的消息归这张工单的执行器决定：范围内的就做，超出范围或属于别的工单的就交还。归属期间这条消息不进评估，没有决定。每张工单有一个只属于它的线程 `ticket:T12`：带着编号说的话（钉钉里回 `T12 把标题改短一点`、`superops reply T12 …`、面板上的回复）落在这里，只到这一张工单。在工单起点的会话里接着说的话（例如终端里用 `--thread` 接着同一个线程）同样归它。

交还的消息在没有别的工单还在决定它时，带着执行器写的原因进入一次新的评估，主 Session 可以把它作为新工作接单、转给别的工单或忽略，但不能转回交还它的那张工单。

工单结束时，放掉它的执行器没读到、也没确认、回答或交还的人的消息；没有别的工单决定它们时，它们进入评估。

执行器为了解上下文而关注的线程（报告里的 `follow`）同样送达消息，但不让工单拥有那里的人的消息，也不唤醒已结束的工单。

到不了任何工单的人的消息走评估这条路，包括线程上的工单是被人停掉的情况。系统事件不管有没有送到工单，都独立地走一遍评估。

## 强度

| 强度 | 情况 |
| --- | --- |
| 明确 explicit | 名单内的人直接对 Agent 说；名单内的人在已有工单的线程上跟进；准入表里设为“明确请求”的格子；带批准凭据的流水线事件 |
| 推断 inferred | 名单外的人在已有工单的线程上跟进（除非他的格子是明确）；准入表里设为“推断候选”的格子；系统来源的事件 |
| 不准入 | 准入表忽略的一切；接单模式为 `off` 时所有推断的情况 |

## 准入表

每个来源的策略里有一张准入表，行是接收范围：钉钉是每个监听的群（行名是群 ID）和 `direct`；终端是 `terminal`；定时是 `schedule`；流水线是 `events`。每行最多三格：

| 格子 | 可选 | 默认 |
| --- | --- | --- |
| 名单内、没对 Agent 说 `listedUnaddressed` | inferred、ignore | inferred |
| 名单外、对 Agent 说了 `unlistedAddressed` | explicit、inferred、ignore | ignore |
| 名单外、没对 Agent 说 `unlistedUnaddressed` | inferred、ignore | ignore；系统来源默认 inferred |

“没对 Agent 说”的两格只在来源收全部消息的范围里有意义：钉钉来源设了 `observe: all` 的群，以及系统来源。终端只收直接说的话。

把“名单外、对 Agent 说了”设成 explicit，那个群里任何人 @兔管家都算明确请求，适合专门的提需求群：

```yaml
policy:
  sources:
    dingtalk:
      admission: {"<群 ID>": {unlistedAddressed: explicit}}
```

准入表是策略版本的一部分。把某一格调弱不会立刻停掉依据它接下的未结束工单，但它们恢复之前复核授权时会失效。

策略里还有一份机器名单 `bots`：名单上的机器发的消息可以成为推断候选，永远不是明确请求。目前没有来源会产生带机器身份的触发，这份名单是空的。

## 规则与接单模式

接单模式是策略的一部分，存在库里，用 `superops mode <off|observe|auto>` 切换（切换后以库里的为准，`policy.yaml` 的 `eval.mode` 只是初始值）：

| 模式 | 效果 |
| --- | --- |
| `off` | 推断的一律不成为候选：没人批准过的定时和业务事件在准入处就被忽略 |
| `observe`（默认） | 推断候选照常研判；本来会接的记为忽略并标注“本来会接单”，不启动 |
| `auto` | 推断候选命中已启用的规则就接单 |

明确的授权在三种模式下都有效：名单内的人直接提的请求，以及人在卡片上批准的动作。先用 `observe`，看过记下的决定再切到 `auto`。

接单模式只管“没人要求的主动工作”。`observe` 下定时起的采集、日报、选题都只记录；但只要有一张工单在等人回答（例如明确请求的工单提了一个发布卡片），人批了，选项里的发布、回复、合并照常执行。反过来，已批准的动作开出的工单再发出的普通事件（例如写稿工单的送审事件）没有凭据，仍然按接单模式处理。

每条规则描述一类可以主动做的工作，写在 `policy.yaml` 的 `policy.rules`：

| 键 | 含义 |
| --- | --- |
| `id`、`name`、`enabled` | 标识、给人看的名字、开关 |
| `instruction` | 这条规则允许做什么，用人话写。它成为工单的范围，也原样给执行器 |
| `when` | `{origin, types, match}`：事件来源、事件类型（可用通配符）、对“对象 + 摘要”的正则。写了它，规则由事件直接命中；不写就是语义规则 |
| `run` | 怎么执行：`executor: agent`（默认）时有 `role`、`agent`、`skill`、`tools`、`effort`、`timeout`、`context`、`worktree`；`executor: script` 时有 `command`、`timeout`；`executor: none` 只留底 |
| `requires_approval` | 这类事件只能来自人选中的卡片选项 |
| `tell` | `never` 不出声 · `needed` 只在要人拍板时 · `always` 结果也发给人 · `digest`（默认）进日报。对按规则开出的工单起作用（包括人批准的事件开出的）；人直接提的请求总会回话 |
| `priority` | 0–3；0 是 P0，不受静默时段和卡片上限限制 |
| `debounce` | 事件到达后先攒这么久再评估，期间同线程的事件并成一批 |
| `max_rounds` | 同一线程上这条规则最多开几张工单 |
| `unless_live` | 同线程上这些规则的工单还没结束时不另开 |
| `after`、`after_max` | 等这些规则的工单跑完再启动，最多等 `after_max`（默认 15 分钟） |
| `credits_per_run` | 每次预计消耗的 Popto 积分，会超出当日预算就不接 |
| `idle_ttl` | 工单闲置多久没等到后续事件就安静结束（默认取 `executor.idle_ttl`，7 天） |

工单的授权记下命中的规则；执行器拿到规则的名字和 `instruction`，按规则主动承接的工单只能做规则允许的那件事。

## 研判：规则直配与语义规则

准入给出强度之后，研判有两条路。

**规则直配。** 系统事件命中了写明 `when` 的规则，不需要模型来判断：规则本身就是团队写下的授权。宿主取这一批里最新的系统事件（有带批准凭据的就取它），按文件顺序找第一条匹配的已启用规则，然后按顺序做确定性的检查，第一条不过的就是决定的原因：

| 检查 | 不过时的决定 |
| --- | --- |
| 没有规则匹配 | 忽略：没有命中已启用的规则 |
| 规则被单独暂停（`superops pause <规则>`） | 忽略：规则已暂停 |
| 规则是 `executor: none` | 忽略：只留底。`tell: always` 的会发一条通知（P0 的发告警） |
| 同线程上这条规则（或 `unless_live` 列的规则）的工单还没结束 | 忽略：事件已通过订阅送达那张工单 |
| 同线程上这条规则的工单数到了 `max_rounds` | 忽略：到了轮数上限 |
| 加上 `credits_per_run` 会超出今日积分预算 | 忽略：超预算 |
| 接单模式不是 `auto`，且事件不带批准凭据 | 忽略：本来会接单 |
| 都过 | 接单。标题是“规则名 · 对象”，范围是规则的 `instruction` |

**主 Session。** 名单内的人的明确请求，以及要按语义规则（没有 `when` 的规则）研判的推断候选，交给模型。主 Session 只路由，不做技术决定，不改写请求。对一个候选它四选一：

- `accept`：新的工作，给标题、范围和一句确认。
- `attach`：消息明确指向某张已有工单（带了编号、引用了它的问题或产出）时转给它；已结束的工单会在原授权下恢复。话题相似不算。
- `stop`：名单内的人明确要求停掉某张工单。
- `ignore`：普通讨论、与规则无关、重复。

推断候选要接单，主 Session 必须对每条已启用、且没被单独暂停的语义规则恰好给出一次判断（命中与否都写原因），确立“确有人要这件事、方向已定”，并至少命中一条；宿主逐项核对，缺一项就不接。接单模式不是 `auto` 时只记录。

`policy.yaml` 目前没有语义规则，所以推断的人的消息（例如 `observe: all` 的群里没 @ 的讨论）在研判处直接忽略，不调用模型。

## 策略版本

规则（`id`、开关、`instruction`、`when`、执行方式、`requires_approval`）、接单模式和各来源的策略部分（名单、机器名单、准入表、可回答人）合起来算出策略版本。每份授权都记着它是在哪个版本下给的。模型、并发、超时、暂停和来源的开关不算在内。

改策略的办法是改 `policy.yaml`（走 MR）或 `local.yaml`，`superops check` 校验，`superops reload` 生效。版本变了之后：

- 进行中的评估作废，记为未完成（原因：研判期间策略变了），它们的触发立刻在新版本下重新排队。
- 受影响的未结束工单各收到一条“策略变了”的输入，说明是哪一种：它依据的规则改了（附新的 `instruction`）或停用了；当初提请求的人已不能发起工作；主动工作不再接单（模式从 `auto` 改走）。执行器按新的规则收尾。
- 不受影响的工单不打扰。变更不会撤销未结束工单的授权。

宿主停着的时候改了策略，启动时会发现版本不一样：进行中的评估同样重来，但这种情况下不逐张告知工单。

## 恢复与停止

已结束的工单保留授权。人在它自己的线程上发消息，会在原授权下恢复同一件工作：不评估，不产生决定，不看是谁发的。系统事件不唤醒已结束的工单。恢复后由执行器判断新消息是否在范围内。

改变授权的只有三件事：接单创建它，人的停止撤回它，复核不过使它失效。被人停掉的工单保持结束，之后什么都不收；那里要的新工作需要重新接单。

- **人在群里说“停”是一条普通的触发**，由评估决定停止；主 Session 的 `stop` 只在强度为明确时生效。执行器不能宣布“人让我停”。
- **面板和终端里的停止是命令**：`superops stop T12 [原因]` 直接作用在工单上，记为人工停止。
- **等待的条件属于来源。** “到某个时间”“等 10 分钟看有没有更多评论”是来源的事；评估从不等待。

### 授权复核

已结束的工单恢复之前、主 Session 把消息转给已结束的工单之前，按当前策略复核它的授权：

- 来源必须还收授权里记下的那个接收范围（来源还开着；流水线来源上那个事件来源没被暂停；钉钉那个群还在监听）。
- 名单内的人直接提出的：他必须还在名单上。
- 人批准得来的（带批准凭据的事件开出的工单）：通过。
- 跟进得来的：明确的通过；推断的需要 `auto` 模式且命中的规则仍启用。
- 准入表某格得来的：按今天的表和发送人今天在不在名单上重新查，给出的强度不能低于当初；推断的还需要 `auto` 模式且命中的规则仍启用。定时和没有凭据的业务事件按规则开出的工单都属于这一种。

复核不过，工单保持结束，等它的消息被放掉：没有别的工单决定它们时进入评估。转给它会被拒绝，新的工作需要重新接单。

## 批红

发布、回复、合并、删除这类对外动作，Agent 只能提议，人来定。这件事由三样东西合起来保证：工单的问题、能回答的人、带凭据的事件。

### 问题

执行器在报告里写 `question`：一句具体的问题，通常带一张卡片。

| 卡片的键 | 含义 |
| --- | --- |
| `title`、`proposal` | 一句话标题（≤ 80 字）、建议怎么办 |
| `reasons`、`risks`、`links` | 依据、照办可能出的问题、文件或 MR 链接 |
| `items` | 明细（今晚要发的每一条、每条线索） |
| `options` | 2–4 个选项，每个有 `key`、`label`，可带 `emit`（选中后发出的事件）、`require_reason`、`record`（`not_doing` / `decision`：把人写的原因记进决策档案） |
| `on_expire`、`expires_at` | 到期按哪个选项处理、什么时候到期 |

宿主把问题渲染成一条带工单编号的消息：标题、建议、依据、风险、编号的明细、每个选项怎么回（`T12 1 → 全部发布`）。它发到引出这个问题的那条人的消息所在的会话，否则发到工单开始的会话（规则起的工单是 home 渠道）。确定性脚本的 `decision_card` 走同一条路。

带卡片的问题有到期时间：卡片的 `expires_at`，否则报告里的 `ttl`，否则 `agents.yaml` 的 `card_default_ttl`（24 小时）。到期时间统一成 UTC 存下来，发给人的卡片上显示成东八区的时间。不带卡片的开放问题不到期，人回的文字作为跟进消息回到工单。

一张工单同一时间只有一个问题。执行器换一个问题会替换原来的，没发出去的那条被撤回。

### 谁能回答

- **用一条消息回答**（钉钉里回 `T12 1`）：消息必须是人发的、落在这张工单的线程上（带编号的回复落在它自己的线程 `ticket:T12`），发送人要么在那个来源的名单 `allowed` 上（全权），要么在 `answerers` 里被限定可以回答这张工单命中的规则。不满足就是“没有审批权限”。
- **本机操作者的命令**：`superops answer T12 1`、面板上的按钮。能调用管理 API 的人就是操作者，不再查名单。

选项用序号或 `key` 指定；选项标了 `require_reason` 而没写原因会被拒绝。选项的 `emit` 和卡片明细一一对应时，可以只批其中几条：`T12 1 3,5`。

### 回答之后

1. 工单记下谁、什么时候、选了什么、原因；问题清掉。
2. 执行器收到一条“人对你的问题作了决定”的输入，接着做或收尾。
3. 宿主把选中选项的 `emit` 逐条发成流水线事件，每条带**批准凭据**：工单编号、问题、选项、回答的人、时间。带凭据的事件强度是明确，接它的规则在任何接单模式下都会开工单；规则被暂停、到了轮数上限、超预算这几项检查照做。
4. 选项有 `record` 且人写了原因时，原因追加进 `not-doing.md` 或 `decisions.md`。
5. 工单的会话里收到一条回执：选了什么、发出了几个已批准的动作。

### 需要人批准的事件

规则标了 `requires_approval: true`，它 `when` 里的事件类型就成了“只有人批过才能发”的类型。流水线来源在事件进入领域之前判断：

- 带批准凭据的：收。
- 可信方发的：收。可信方只有三种：宿主自己（开出 MR 后发的 MR 事件、入库程序追加的事件、钉钉里审批人下的指令）；脚本工单输出的后续事件；带着宿主令牌调用 `/v1/events` 的确定性脚本。令牌每次启动随机生成，只通过环境变量交给宿主拉起的脚本。
- 其余的一律记为过滤，原因 `needs_approval`：执行器在报告的 `events` 里发的；不带令牌调用 `/v1/events` 发的，包括操作者手敲 `superops emit content.publish.approved`。触发照样留底，看得到是谁想发什么。

Agent 这一侧另有两处收紧：它输出的事件里以 `_` 开头的键全部丢掉（宿主内部的标记混不进来）；它的环境变量里没有管理 API 的地址和令牌。

这是默认的防线，不是安全边界。Agent 和宿主以同一个系统用户运行，能运行任意程序的档位原则上找得到宿主的端口和进程；要真正隔离，得用单独的系统账号。

所以“写稿”“开发”“发布”“回复”“合并”“清理”这六条规则的入口事件，Agent 自己发不出来；它只能把事件写进卡片选项，等人选。发布和评论回复的执行脚本自己还有一道账本检查：批准超过 24 小时的不执行，同一个动作只执行一次。

### 到期

问题到期没人回答，宿主按卡片的 `on_expire` 处理；卡片没写就取最后一个不带 `emit` 的选项。到期的回答不带批准凭据，所以即使安全选项里写了事件，需要批准的类型也发不出去；只有登记类的事件（如把线索记为“不跟进”）能发出。工单会话里会有一条回执：“到期没有回复，按「…」处理”，后面写“登记了 N 项（不做对外动作）”或“无后续动作”。

## 评估没完成时

研判的时限（`eval.timeout_seconds`，默认 600 秒）从候选交到研判方开始算。超时的评估把触发重新排队；连续重排两次之后，第三次超时记为未完成。主 Session 的调用失败、或它的决定被宿主拒绝（例如想把推断候选当明确请求接单），也记为未完成；线程上后来的触发可以开始新的评估。策略变更造成的未完成会立刻重新排队。

最近一小时有未处理的未完成决定时，健康板的 `evals` 报错。面板和 `superops status` 只在它不到 24 小时、仍是线程上最新的决定、没被忽略、线程也没在排队或评估时才把它列为问题。人可以重新评估那条触发（`superops reevaluate <trigger_id>`），或者忽略这个问题（`superops dismiss <decision_id>`）。
